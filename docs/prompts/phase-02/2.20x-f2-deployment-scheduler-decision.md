## Requisitos del trigger

- invocación periódica bounded, inicialmente cada cinco minutos;
- runtime efectivo superior a 45 segundos y margen de cierre;
- secretos server-only y autenticación máquina-a-máquina sin Clerk;
- boundary HTTPS autenticado que no acepte tenant, Store ni Connection;
- reutilización directa de `runIncrementalEventMaintenance`;
- tolerancia a invocaciones duplicadas mediante locks, leases y CAS existentes;
- acceso saliente a Supabase y Mercado Libre, logs seguros y coste controlado;
- política explícita para recuperar un maintenance run abandonado si el proceso
  muere después de `start` y antes de `finalize`.

## Opciones auditadas

| Opción | Compatibilidad y límite | Evaluación |
| --- | --- | --- |
| Vercel Cron | Next.js nativo; invoca una route HTTPS con `CRON_SECRET`. El budget de 45 s requiere configurar duración. Cadencia de pocos minutos requiere Pro: Hobby admite sólo una ejecución diaria. | Preferida únicamente si Vercel Pro es el deployment aprobado. |
| Supabase Cron + HTTP | `pg_cron` + `pg_net` puede invocar un boundary y usar Vault. | Hosting-neutral, pero acopla scheduling a DB e introduce configuración remota adicional; alternativa, no default. |
| Netlify Scheduled Functions | Integración propia y límite fijo de 30 s para scheduled functions. | No compatible directamente con el budget actual de 45 s; además el repo no está configurado para Netlify. |
| Cron/timer self-hosted | Host cron o systemd timer invoca el boundary del contenedor. | Preferida si se aprueba Docker/VPS; buena paridad y runtime, con mayor carga operativa. |

## Recomendación

Conservar un adaptador delgado:

`deployment scheduler → authenticated HTTP route → runIncrementalEventMaintenance`

La autenticación inicial recomendada es un Bearer secret aleatorio, exclusivo
del scheduler y guardado en el secret store de la plataforma. No se inventa ni
versiona un valor real. El backend de scheduling debe ser deployment-native:
Vercel Cron si se aprueba Vercel Pro, o cron/systemd timer si se aprueba
Docker/VPS. No corresponde implementar F3 hasta que el usuario elija una de
esas plataformas y se defina la recuperación de runs abandonados.

## Failure model

Una invocación duplicada no debe duplicar eventos: el maintenance lock por
Connection y los leases/CAS por evento conservan correctness. Una ejecución
retrasada deja backlog durable para el ciclo siguiente. Outages de provider o
DB deben producir error seguro y retry posterior, sin convertir al scheduler
en source of truth.

Existe un gap previo a producción: un hard timeout o crash entre start y
finalize puede dejar un maintenance run `running` sin reclaim automático. F3
debe resolverlo con una semántica bounded y auditable antes de activar cron.
