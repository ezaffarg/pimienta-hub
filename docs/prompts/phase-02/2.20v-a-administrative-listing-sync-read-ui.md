# Fase 2.20V-A — Administrative listing sync operations read UI

## Objetivo

Agregar una superficie administrativa de sólo lectura para inspeccionar el
historial de listing sync runs. Este bloque consume los contratos cerrados en
[2.20T](./2.20t-sync-run-orchestration-observability.md) y
[2.20U](./2.20u-administrative-stale-run-recovery.md) sin repetir su diseño.

## Scope

- Ruta dashboard server-first protegida para Owner y Manager persistentes.
- GET interno tenant-bound y listado reciente con límite administrativo.
- Reutilización del read model 2.20U para stale y recovery eligibility.
- Store, Connection, status, timestamps, progress y error seguro.
- Tabla accesible y responsive con filtros acotados, orden reciente, loading,
  error y empty state.

## Exclusiones

No se agregan recovery mutations, acciones de sync, formularios, provider
calls, OAuth, reconnect, refresh, migrations, schema changes, writes remotos,
rediseño de navegación ni cierre Git.

## Diseño elegido

El flujo será UI → GET interno/server prefetch → servicio 2.20U → repositories
tenant-bound → DB. La página hidratará TanStack Query y el cliente usará
`useSuspenseQuery`; ninguna credencial ni acceso privilegiado cruzará al
browser. El listado se limitará server-side, con `started_at DESC` por defecto.

No se agrega entrada al sidebar en este bloque: el filtro de navegación vigente
usa roles Clerk en cliente y no conoce la autoridad `hub_memberships`. La ruta
seguirá protegida server-side; una navegación business-role-aware requiere un
diseño separado para no convertir UX en autorización.

## Archivos previstos

- Ruta dashboard y estados `loading`/`error`.
- GET interno de listing sync runs.
- Repository y servicio/read model 2.20U.
- Feature UI provider-agnostic con query options y tabla.
- Tests focalizados de autorización, contrato y presentación.
- Documentación técnica mínima de API, arquitectura, gobierno y handoff.
