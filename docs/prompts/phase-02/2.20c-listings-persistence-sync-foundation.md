# FASE 2 — 2.20C LISTINGS PERSISTENCE + SYNC FOUNDATION

Base `eff2796`. Objetivo aprobado: crear una foundation local, provider-agnostic y server-only para persistir `ExternalListingSummary` mediante sync idempotente. El flujo futuro es Provider API → normalización → sync idempotente → `listings` → producto/UI.

Se auditan sólo migrations, Stores, Connections, tenant binding, repositories, contrato core, normalización 2.20B y documentación de API/base de datos. La tabla debe ser `listings`, nunca una tabla específica de Mercado Libre ni `products`; su identidad es `connection_id + external_listing_id`, no título, SKU o permalink.

La fila mantiene Organization, Store y Connection; bindings se derivan server-side. Precio usa `numeric`, SKU es nullable y sólo usa `SELLER_SKU`; no hay fallback a `seller_custom_field`. Status es texto normalizado sin enum provider-specific. No se guardan payloads raw ni se borra por ausencia de una página. `last_synced_at` registra observación correcta.

La migration será forward-only, habilitará RLS sin policies de navegador, revocará `PUBLIC`/`anon`/`authenticated` y otorgará DML sólo a `service_role`. Se crearán repository server-only (`upsertMany`, búsquedas y conteo) y un sync service canónico, sin lógica de Mercado Libre en repository. La unique key y upsert deben impedir duplicados concurrentes; mismatches de ownership fallan cerrados.

Se autorizan tests relevantes, typecheck, lint y `supabase db reset` local. Se prohíben `db push` remoto, SQL remoto, persistencia real de la listing de E.A.ZOCOOL, llamadas/mutaciones Mercado Libre, UI, workers, cron, tablas de producto, `git add`, commit y push.
