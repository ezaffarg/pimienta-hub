# Fase 2 — 2.20N: Controlled real Mercado Libre reconnect

## Mandato archivado

Base: `4946317`. La Connection activa de E.A.ZOCOOL tiene una Store, una
Connection, un `integration_secret`, versión de credencial `1` y lease libre.
El refresh persistido se considera consumido o no reutilizable tras 2.20K. La
causa histórica del CAS continúa `STILL_UNKNOWN`; las foundations y el
diagnóstico de CAS están validados.

Objetivo: realizar un OAuth nuevo, oficial y manual para la misma cuenta y usar
el flujo de reconnect existente. Debe localizar Store y Connection existentes,
reemplazar credenciales cifradas de forma segura, incrementar la versión,
conservar la Connection activa y no crear duplicados. No se ejecutará listing
sync.

Precondiciones: `HEAD == origin/develop`; sólo se permiten como pendientes los
prompts 2.20E y 2.20L. El precheck remoto es read-only. Está prohibido invocar
refresh con la credencial persistida, usar `grant_type=refresh_token`, revelar
state, authorization code, tokens, ciphertext, secretos o headers. Si la
redirect URI actual no es alcanzable o requiere nuevo túnel, detenerse antes de
OAuth y pedir que el usuario configure el nuevo callback en DevCenter.

El callback debe validar state, actor, Organization, provider, purpose, expiry y
single-use; la identidad debe ser E.A.ZOCOOL. La finalización esperada es
reconnect de la Connection existente, con `integration.reconnected` y sin
`store.created` ni `integration.connected` como conexión nueva. Después se
autoriza una sola lectura `GET /users/me`; no listings. No hay cierre Git hasta
un checkpoint posterior.

## Precheck y STOP — reconnect activo no alcanzable

Precheck Git: `HEAD` y `origin/develop` coinciden en `4946317`. El remoto
confirmó Owner persistente 1, Store 1, Connection 1 activa, Assignments 0,
`integration_secrets` 1, Listings 0, `credential_version=1` y lease libre. La
redirect URI configurada respondió HTTP 400 sin parámetros OAuth, por lo que el
host público y callback son alcanzables; no hace falta un túnel nuevo.

Sin embargo, `completeMercadoLibreOAuth()` busca la Connection por provider y
external account y, si está `active`, lanza `already_connected` antes de crear
la pending authorization. Sólo retorna `READY_FOR_RECONNECT` cuando la
Connection existente está `disabled`. El finalizador SQL sí contempla pending
con purpose `reconnect`, pero ese camino no es alcanzable para la Connection
real activa.

**STOP:** no se creó OAuth attempt, no hubo callback, token exchange,
`GET /users/me`, refresh, reconnect ni escritura remota. Hace falta un cambio
mínimo y testeado del runtime para permitir `purpose=reconnect` sobre una
Connection activa del mismo tenant, sin permitir cross-tenant ni onboarding
duplicado. Requiere una aprobación nueva antes de implementarlo.

## Continuación — ejecución real después de 2.20O

Tras el cierre de 2.20O (`3058308`), se autoriza exactamente un Authorization
Code OAuth nuevo con `purpose=reconnect` para E.A.ZOCOOL. El refresh token
persistido anterior es no reutilizable y está prohibido invocar refresh sobre él.
Antes de crear el intento se confirma Git sincronizado, redirect URI usable,
configuración presente sin revelar valores, master key válida y el estado remoto
esperado: Owner 1, Store 1, Connection activa 1, assignments 0,
`integration_secrets` 1, listings 0, versión 1 y lease libre.

La autorización de Mercado Libre es obligatoriamente humana. Después de crear
un único intento se debe detener la automatización y esperar el callback. El
callback y finalización deben validar state/actor/tenant/provider/purpose,
intercambiar el code una sola vez, comparar la identidad con la Connection,
reutilizar Store y Connection, reemplazar una única fila de secretos, incrementar
la versión y auditar `integration.reconnected`. No hay retry, refresh, listings,
migración ni cierre Git.

## Blocker temporal — Clerk SignIn UI

Durante 2.20N, `/auth/sign-in` carga el shell visual de autenticación pero no
renderiza la interfaz de Clerk en el panel derecho. OAuth queda pausado. Se
auditan rutas, provider, proxy, estilos y configuración de Clerk sin ejecutar
OAuth ni realizar escrituras remotas.

Diagnóstico: el formulario funciona en `localhost`, donde Clerk llega a
`ready`, pero en el host público actual Clerk quedaba en `loading` y el
WebSocket HMR devolvía `502`. `next.config.ts` mantenía sólo el hostname de un
túnel previo en `allowedDevOrigins`; se reemplaza por el hostname temporal
vigente. No se cambia Clerk, variables de entorno, OAuth ni autorización.

Resultado: bloqueador Clerk resuelto tras reiniciar el entorno. El callback
real de reconnect dejó una pending activa, correctamente ligada a la
Organization, membership y Connection existentes, con credenciales cifradas y
expiración futura. No se registran valores de callback ni secretos.

**RECONNECT_FINALIZATION_GAP:** la RPC server-only existente
`finalize_admin_pending_integration_onboarding` consume la pending pero, si la
Connection encontrada ya está `active`, devuelve `already_connected` antes de
reemplazar credenciales, incrementar `credential_version` o emitir
`integration.reconnected`. No se la invoca: hacerlo descartaría las nuevas
credenciales. Requiere una subfase técnica aprobada para corregir el flujo
atómico de reconnect activo.
