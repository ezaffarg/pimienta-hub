# Fase 2.20X-F3-B — Coolify / Docker production implementation

Fecha: 2026-08-29. Estado: **IMPLEMENTACIÓN LOCAL PASS**.

## Objetivo

Implementar localmente la foundation productiva aprobada en F3-A para
Hostinger VPS → Ubuntu LTS → Docker → Coolify: un Dockerfile standalone
canónico, healthcheck público técnico y un boundary interno autenticado para
invocar el mantenimiento incremental existente.

## Contratos confirmados

- Bun instala y construye con lockfile; Node.js non-root ejecuta `server.js`.
- El container escucha en `0.0.0.0:3000`, copia sólo standalone, static y public
  y no contiene secretos ni ejecuta migrations al iniciar.
- `GET /api/health` es determinista y no usa Clerk, DB o providers.
- `POST /api/internal/maintenance/incremental-events` usa un Bearer secret
  dedicado, no Clerk ni autoridad tenant del caller, y delega directamente en
  `runIncrementalEventMaintenance`.
- Coolify conserva autoridad sobre schedule/restart; cadence cinco minutos,
  budget 45 segundos y stale reclaim diez minutos.

## Límites

No se configura Coolify, Traefik, DNS, TLS, Hostinger ni scheduler reales. No
se aplican migrations, no se llama a Supabase remoto ni Mercado Libre y no se
realiza cierre Git.

## Validación y checkpoint

El Docker build standalone pasó con variables públicas sintéticas. Un container
efímero arrancó healthy en `0.0.0.0:3000` como usuario `node`; health devolvió
200 y la ruta scheduler rechazó requests sin Bearer y con Bearer incorrecto.
No se invocó el scheduler con el secret correcto fuera de tests mockeados.

Tests de health 2/2, scheduler 8/8 y proxy 2/2 pasaron; la regresión focalizada
de orquestador, webhook, seguridad y routes pasó 36/36. Suite 365/365,
typecheck, lint y `git diff --check` pasaron. Los avisos LF→CRLF del checkout y

No hubo remote, provider, migrations, scheduler real ni cierre Git. El próximo
gate es F3-C para deploy y validación remota controlados.
