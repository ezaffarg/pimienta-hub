# Fase 2 — Subfase 2.1: schema SQL exacto y estrategia de migraciones

Status: **COMPLETED — diseño documental; commit pendiente**

## Purpose

Definir el schema PostgreSQL que podrá aplicar la Subfase 2.2 y un flujo de migraciones SQL reproducible con Supabase CLI. Esta subfase no crea tablas, migraciones, `supabase/`, repositorios ni acceso a base de datos.

## Decisions

- El diseño objetivo tiene cuatro tablas: `hub_memberships`, `stores`, `store_assignments` y `connections`.
- Los IDs internos son `uuid`; los IDs de Clerk y de cuentas externas son `text`; fechas usan `timestamptz`.
- Roles, estados y providers usan `text` con `CHECK`; los roles son Owner, Manager, Employee y Client; el conjunto de providers coincide con `IntegrationProvider` existente, incluido `mercado-libre`.
- `store_assignments` y `connections` usan FKs compuestas que incluyen `organization_id`; no existe una tabla local de Organizations.
- Las conexiones no almacenan secretos OAuth. `scopes` usa `text[]`; tokens y cifrado se difieren a Fase 3.
- `updated_at` será mantenido explícitamente por repositorios futuros, sin trigger genérico inicial. No se usa `deleted_at` por defecto.
- La unicidad de provider/cuenta externa es parcial y conserva la reserva mientras la conexión esté conectada, expirada, requiera reautorización o tenga error. Una conexión disabled/disconnected permite un futuro workflow explícito de transferencia.
- Se recomienda Supabase CLI como `devDependency` con versión exacta, invocada con Bun. La instalación y los cambios en `package.json`/`bun.lock` requieren aprobación separada.
- Las migraciones futuras vivirán en `supabase/migrations/<UTC timestamp>_<descripcion_en_snake_case>.sql`, creadas por CLI. Cada corrección será forward-only; la validación local repetirá el schema desde cero con `supabase db reset` y Docker.
- RLS, `supabase link`, `db push`, bases remotas y generación de tipos quedan fuera de esta subfase.

## Restrictions

No instalar dependencias ni modificar `package.json` o `bun.lock`. No crear `supabase/`, migraciones ni tablas. No implementar repositorios, Store Scope, guards, endpoints, bootstrap de Owner, OAuth, conexiones funcionales, RLS, UI, `git add`, commit o push.
