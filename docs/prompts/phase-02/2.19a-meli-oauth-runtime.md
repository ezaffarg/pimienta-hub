# Fase 2 — 2.19A Mercado Libre OAuth Runtime Setup

> Implementar el runtime OAuth técnico sin autorizar una cuenta real, crear Store/Connection/assignment reales ni ejecutar OAuth real.

## Estado y decisiones de entrada

- Current Owner persistente: 1; base remota validada y hardened; RLS y privilegios RPC validados.
- Stores, Connections, assignments, OAuth attempts, secrets y audit events: 0.
- OAuth oficial: Authorization Code server-side; `/users/me` entrega el `id` usado como `external_account_id` y `nickname` es sólo display.
- `state` debe ser opaco, actor/Organization-bound, expirable y single-use. Tokens son server-only y cifrados fuera de `connections`.
- Owner/Manager pueden conectar; Client sólo self-connect/reconnect; Employee queda denegado. Store/Connection debe ser transaccional, después de resolver la identidad externa.

## Alcance solicitado

Auditar el adapter Mercado Libre, utilidades OAuth, services de attempts/secrets, authorization context, providers, documentación OAuth y convenciones de rutas. Definir sólo las variables `MERCADO_LIBRE_CLIENT_ID`, `MERCADO_LIBRE_CLIENT_SECRET`, `MERCADO_LIBRE_REDIRECT_URI` (más la ya existente `INTEGRATION_SECRETS_MASTER_KEY`), sin valores ni exportación client-side.

El runtime previsto incluye helper server-only de configuración fail-fast; cliente provider server-only para authorization URL, token exchange, `/users/me` y normalización de errores; PKCE S256 sólo si la Developers Application lo habilita; servicio start que deriva contexto y permiso server-side, crea attempt y devuelve URL; ruta POST server-side con estrategia CSRF/origin; y callback que valida/consume state antes de token exchange, normaliza identidad y devuelve un preview no sensible.

El callback no puede aceptar Organization, actor, rol o Store como autoridad. Debe manejar denegación, state inválido/expirado/consumido, respuestas externas inválidas y errores normalizados sin secretos. No puede filtrar code, client secret, access/refresh token ni raw provider responses. El `redirect_uri` es exacto y estático. La sesión de callback debe conservar binding server-side sin convertir state en bearer token reusable.

## Persistencia temporal obligatoria

Antes de persistir una Store/Connection, tokens resultantes del callback requieren una estrategia server-only segura: material cifrado asociado correctamente al attempt, o una estructura temporal específica para 2.19B. Nunca query params, cookies browser-readable ni estado frontend. Si el schema no lo soporta, detenerse con `NEEDS DESIGN`; no improvisar una migration en 2.19A.

## Límites

No ejecutar onboarding admin/client ni crear Store, Connection, assignment, secreto remoto o audit event. No abrir authorization URL real, usar cuenta real, enviar code real, generar attempt remoto manual, migration, `db push`, OAuth real, webhooks, sync, Fase 3, `git add`, commit o push. Actualizar sólo API OAuth y este prompt, salvo bloqueo operativo real en handoff.

## Resultado de auditoría — NEEDS DESIGN

La migration vigente define `oauth_attempts` sólo para state digest, binding de actor/Organization, expiración, consumo y verifier PKCE cifrado. `integration_secrets` exige una `connection_id` mediante FK compuesta con `connections`. Por tanto no existe almacenamiento server-only para access/refresh tokens temporales ni una identidad externa verificada antes de crear una Connection.

Como este checkpoint prohíbe crear Store/Connection y no autoriza migration, completar callback + token exchange dejaría tokens sueltos o descartaría una autorización ya consumida sin poder finalizar onboarding. Se detiene la implementación antes de rutas, configuración o llamadas OAuth. La decisión requerida para 2.19B es aprobar una estructura temporal server-only ligada al `oauth_attempt` (cifrado, expirable y de consumo único) o autorizar una transacción que persista el onboarding en el mismo callback.

## Continuación — approved pending authorization foundation

Se aprueba resolver exclusivamente la transición callback OAuth → token exchange → `GET /users/me` → identidad verificada → pending onboarding → onboarding definitivo posterior. No se ejecuta OAuth real.

La nueva foundation se llamará `oauth_pending_authorizations`: representa una autorización OAuth ya verificada, todavía no convertida en Connection. Cada fila se vincula a un `oauth_attempt`, con máximo una pending authorization por attempt, y conserva binding de Organization, actor membership, provider y purpose mediante constraint/FK segura, nunca desde datos browser-supplied.

El esquema mínimo contiene UUID, attempt, Organization, actor, provider, purpose, `external_account_id`, `display_name` nullable, access token cifrado, refresh token cifrado nullable, expiración del access token, metadata mínima allowlisted, versión de clave, expiración propia de la pending authorization, `consumed_at` y timestamps. No guarda respuestas completas ni email de Mercado Libre. `external_account_id = String(id)` y `display_name = nickname` sólo proceden de `GET /users/me`; Store.name sigue siendo humano, editable y no es identidad OAuth.

Reutilizar exactamente AES-256-GCM e `INTEGRATION_SECRETS_MASTER_KEY`; nunca plaintext. El TTL recomendado es corto, 10–30 minutos, y se adopta 20 minutos. La finalización consume atómicamente la pending; callbacks repetidos no producen dos pending válidas.

La tabla debe tener RLS, cero policies browser-facing, `PUBLIC`/anon/authenticated revocados y DML sólo para `service_role`. No exponer RPC pública ni acceso mediante cliente Supabase browser-side. Las primitives server-only crean, leen para actor y consumen validando Organization, actor, provider, purpose, expiración y estado consumido.

La finalización futura será: pending + Store.name confirmado → transacción definitiva. Para admin: Store, Connection, integration_secrets, audit y pending consumida; para Client se añade assignment. Connection disabled se reactiva; cuenta activa devuelve `already_connected`; cross-tenant devuelve conflicto opaco. Los tokens no entran en audit events. La limpieza futura elimina sólo pending expiradas; no crear cron/worker ahora.

Crear una migration forward-only; no editar 2.16/2.17 ni aplicarla remoto. Probar creación, cifrado, actor/Organization/provider binding, expiración, consumo único, duplicate attempt y paths de Connection; ejecutar reset local, tests relevantes, typecheck, lint y `git diff --check`. No build si no cambian routes. No hay `db push`, SQL remoto, OAuth real, Store/Connection/assignment reales ni cierre Git.
