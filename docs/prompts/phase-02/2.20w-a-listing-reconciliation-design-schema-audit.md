# Fase 2.20W-A — Listing reconciliation design & schema audit

## Objetivo y alcance

Auditar el modelo y el flujo vigente de Listings para diseñar una reconciliación
fail-closed ante ausencias en scans posteriores. Este subhito es exclusivamente
de auditoría y diseño: no implementa reconciliación, migration, código productivo,
tests, operaciones remotas ni llamadas al provider.

El repositorio es la Source of Truth. Los antecedentes operativos están en
[2.20T](./2.20t-sync-run-orchestration-observability.md),
[2.20U](./2.20u-administrative-stale-run-recovery.md) y
[2.20V](./2.20v-a-administrative-listing-sync-read-ui.md).

## Findings, diseño y decisión de schema

### Modelo e identidad vigentes

`public.listings` usa `unique (connection_id, external_listing_id)` como identidad
idempotente. Cada fila conserva `organization_id`, `store_id` y `connection_id`,
y una FK compuesta hacia `connections (id, store_id, organization_id)` impide
bindings cross-tenant o cross-Store. Reconnect target-bound reutiliza la misma
Connection sólo después de validar provider e identidad externa; por eso una
rotación de `credential_version` no cambia la pertenencia histórica del Listing.

Los campos relevantes actuales son: IDs y scope; `external_listing_id`; atributos
normalizados, incluido `status`; timestamps `provider_created_at`,
`provider_updated_at`, `last_synced_at`, `created_at` y `updated_at`.
`last_synced_at` equivale a evidencia positiva de última observación persistida,
pero no identifica el run. No existen `last_seen_sync_run_id`, estado missing,
`missing_since`, contador de ausencias ni join run-item.

El upsert actual actualiza `last_synced_at` y `updated_at` en cada observación,
aunque el resto del Listing no cambie. No existe asociación durable run ↔ Listing.

### Flujo y completeness actuales

El flujo vigente es seller discovery → paginación offset/scan → details en batches
de hasta 20 → upsert por batch → checkpoint → finalize. El servicio deduplica IDs,
pero `succeeded` sólo significa que el flujo terminó sin failure contabilizada.
No valida que `discovered = requested = fetched = persisted`, que el total del
provider se haya alcanzado ni que el cursor haya terminado de forma autoritativa.
Por lo tanto, `succeeded` no equivale a `COMPLETE_AUTHORITATIVE_SCAN`.

El endpoint real es `GET /users/{seller_id}/items/search`, sin filtro de status;
para más de 1000 resultados usa `search_type=scan` y `scroll_id`. La
[documentación oficial](https://developers.mercadolibre.com.ar/es_ar/api-docs-es/items-y-busquedas)
lo describe como listado de los ítems de la cuenta del vendedor y documenta el
scroll hasta `null`. No garantiza un snapshot estable durante todo el recorrido,
no define de forma cerrada qué status incluye el request sin filtro y recomienda
notificaciones para mantener consistencia. `active`, `paused` y `closed` están
normalizados y probados localmente; otros estados siguen abiertos. En consecuencia,
la semántica necesaria para marcar ausencia permanece `PROVIDER_SEMANTICS_UNRESOLVED`.

### Contrato COMPLETE_AUTHORITATIVE_SCAN

Un run sólo podría ser autoritativo si se cumplen todas estas condiciones:

1. Scope fijo y validado: Organization + Store + Connection + provider + external
   account identity.
2. Connection activa y run original todavía `running`, nunca terminalizado por
   stale recovery.
3. Query profile explícito, sin filtros reductores, cuya cobertura esté demostrada.
4. Paginación agotada por el mecanismo oficial; cursores no repetidos, page cap no
   alcanzado, total consistente y `discovered` igual al universo declarado.
5. Cero fallos de discovery, details o persistencia, con
   `discovered = requested = fetched = persisted` y `failed = 0`.
6. Cada Listing observado queda ligado durablemente al mismo run.
7. El run sigue siendo el vigente para la Connection al reconciliar y finalizar.
8. Reconciliación, counters terminales y audit se confirman atómicamente.

Ante cualquier duda o incumplimiento, el run no puede marcar ausencias.

### Estrategias evaluadas

| Estrategia | Evaluación |
| --- | --- |
| `last_seen_at` | Ya existe funcionalmente como `last_synced_at`, pero no prueba qué run observó la fila ni protege por sí solo contra workers viejos. |
| `last_seen_sync_run_id` | Evidencia mínima, durable, depurable e idempotente; permite comparar una fila con un run autoritativo sin guardar payloads. |
| generation/epoch | Segura, pero duplica orden/versionado que ya aporta `listing_sync_runs.started_at` y exige otra secuencia. |
| `listing_sync_run_items` | Máxima trazabilidad, pero multiplica filas por cada scan y no es necesaria para el primer reconciliador. |

Recomendación: `LAST_SEEN_RUN_ID`, reutilizando `last_synced_at` como timestamp de
observación positiva y sin crear una join table.

### Decisión de schema

`SCHEMA_EXTENSION_REQUIRED`. La migration futura 2.20W-B debería proponer
exactamente:

- `listing_sync_runs`: unique auxiliar
  `(id, connection_id, store_id, organization_id)` para una FK compuesta;
  `authoritative_scan boolean not null default false`;
  `missing_candidate_count bigint not null default 0 check (... >= 0)` y
  `reappeared_count bigint not null default 0 check (... >= 0)`.
- `listings`: `last_seen_sync_run_id uuid null`; `reconciliation_state text not
  null default 'seen' check (reconciliation_state in ('seen',
  'missing_candidate'))`; `missing_since timestamptz null`; `missing_count bigint
  not null default 0 check (missing_count >= 0)`.
- FK compuesta
  `(last_seen_sync_run_id, connection_id, store_id, organization_id)` hacia
  `listing_sync_runs (id, connection_id, store_id, organization_id)`, con
  `ON DELETE RESTRICT`.
- CHECK de coherencia: `seen` exige `missing_since is null` y
  `missing_count = 0`; `missing_candidate` exige `missing_since is not null` y
  `missing_count > 0`.
- Índice de reconciliación por
  `(connection_id, reconciliation_state, last_seen_sync_run_id)`.
- RLS y grants sin cambio conceptual: sin policies browser-facing; DML/RPC sólo
  para `service_role` server-only.
- Backfill conservador: filas existentes quedan `seen`, contador cero y
  `last_seen_sync_run_id = null`; no se inventa vínculo con un run histórico.

`CONFIRMED_MISSING` se difiere: no hace falta incorporarlo al primer schema ni
autoriza hard delete. Un primer scan autoritativo ausente crea
`MISSING_CANDIDATE`; cualquier observación posterior restaura `SEEN`, conserva la
misma identidad y limpia evidencia missing. Una futura confirmación debería exigir
como mínimo dos scans autoritativos consecutivos y un umbral temporal configurable;
el valor temporal queda pendiente hasta resolver las semánticas del provider.

### Threat model de false missing

| Amenaza | Puede causar false missing | Mitigación fail-closed |
| --- | --- | --- |
| Run partial, timeout, 429 o 5xx agotado | Sí | Nunca reconciliar desde `partial`/`failed`. |
| Página omitida, cursor defectuoso o page cap | Sí | Probar agotamiento, unicidad de cursor y total; si falla, no autoritativo. |
| Persist failure | Sí | Exigir igualdad de counters y evidencia por run. |
| Reconnect o cambio de identidad | Sí | Scope fijo; validar misma Connection/provider/external identity. |
| Refresh durante scan | Sí | Pin de identidad; cualquier fallo invalida completeness. |
| Eventual consistency | Sí | Candidate primero; al menos dos scans para futura confirmación. |
| Filtro implícito o por status | Sí | Query profile explícito; bloquear mientras su cobertura sea ambigua. |
| Alta/baja durante el scan | Sí | No confirmar en un solo scan; snapshot semantics pendientes. |
| Retry exitoso | No por sí solo | Aceptar sólo la respuesta final válida; agotamiento invalida. |
| Provider IDs duplicados | Sí, si ocultan progreso | Deduplicar y contrastar total/counters. |
| Stale-run recovery | Sí | Un run recuperado administrativamente nunca es autoritativo. |

### Concurrencia, atomicidad y pseudoflujo 2.20W-B

1. El caller autorizado entrega Organization, Store, Connection, actor e
   idempotency key; ningún ID del browser decide scope.
2. Start conserva el gate single-running y crea el run con
   `authoritative_scan = false`.
3. El servicio fija provider, external account y query profile; recorre discovery
   registrando total, modo, cursores y terminación en memoria controlada.
4. Cada batch usa una operación run-aware que bloquea/valida que el run siga
   `running`, upserta Listings, liga `last_seen_sync_run_id` y limpia estado missing
   de reapariciones. Un worker recuperado o viejo no puede escribir evidencia.
5. Checkpoints siguen siendo observabilidad, no resumability.
6. El servicio calcula eligibility con todas las condiciones de
   `COMPLETE_AUTHORITATIVE_SCAN`. Si falta una, finaliza sin reconciliación y sin
   marcar ausencias.
7. Si pasa, una única RPC/transacción bloquea Connection y run, revalida scope,
   estado y ausencia de un run más nuevo; marca como candidates sólo Listings del
   mismo Organization + Store + Connection cuyo `last_seen_sync_run_id` no sea el
   run actual; actualiza counters y finaliza `succeeded`/autoritativo con el audit
   terminal.
8. Retries del mismo run son idempotentes. Un run terminal o más viejo no puede
   volver a reconciliar.

No se recomienda un audit por Listing candidate: produciría ruido. El audit
terminal existente debería incluir sólo counters agregados allowlisted. Los
counters persistentes recomendados son `missing_candidate_count` y
`reappeared_count`; `confirmed_missing_count` queda diferido junto con ese estado.

El estado de reconciliación es canónico y provider-agnostic. `status` continúa
siendo el status observado del provider, sin inventar mapping común para
`active`, `paused`, `closed`, `under_review`, `inactive`, deleted/removed o
unknown.
