# 2.20X-F3-C-LOCAL-2D3C14 — Durable credential refresh diagnostics

## Objetivo

Agregar observabilidad durable, segura y separada para el refresh OAuth que
ocurre dentro de missed-feed maintenance, sin ejecutar providers ni modificar
la semántica de credenciales, lease, CAS o cooldown.

## Alcance

- Trazar el pipeline canónico desde `getValidAccessToken()` hasta cleanup.
- Conservar un stage allowlisted, el subtipo CAS existente y contadores OAuth
  separados de `/users/me` y `/missed_feeds`.
- Persistir los datos mediante checkpoint, finalize y summary server-only.
- Mantener filas históricas en `NULL/UNKNOWN` y nuevos runs con contadores cero.
- Validar exclusivamente con mocks, fixtures locales y PostgREST local.

## Límites

- Cero provider calls, refresh real, maintenance, OAuth, reconnect o scheduler.
- Una sola migration forward aditiva; apply remoto sólo tras gates locales.
- Sin tokens, ciphertexts, payloads, headers ni errores libres persistidos.
- Sin commit ni push; `.vscode/tasks.json` permanece fuera de scope.

## Resultado

PASS local y remoto. Los tests focalizados pasaron 55/55, además de typecheck,
lint, reset/migration local, matriz nueva y regresiones. Los payloads old/new de
checkpoint y finalize y los campos nuevos del summary resolvieron por el path
real `supabase-js -> PostgREST .rpc()` tanto local como remoto.

La migration `20260902113000_durable_credential_refresh_diagnostics.sql` quedó
aplicada al proyecto canónico. Los tres runs históricos conservan los cuatro
campos en `NULL/UNKNOWN`; no se crearon fixtures remotos. La Connection real
permanece en versión 4, access expirado, refresh presente y lease libre. No se
ejecutaron provider calls, refresh real, maintenance, OAuth, reconnect ni
scheduler. El siguiente bloque puede hacer commit/deploy y autorizar por
separado un único retry observable.
