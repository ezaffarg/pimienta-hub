# Fase 2.20V-B — Administrative listing sync recovery UI

## Objetivo

Agregar confirmación y ejecución administrativa de recovery sobre la UI
read-only de 2.20V-A, reutilizando sin cambios el boundary cerrado en 2.20U.

## Scope

- Acción sólo en runs `RECOVERABLE_AS_SUCCEEDED` o `RECOVERABLE_AS_FAILED`.
- Dialog accesible con Store, Connection, status, stale, target y reason.
- POST al endpoint 2.20U con taxonomy cerrada.
- TanStack mutation, prevención de doble submit, toast seguro e invalidación de
  la query administrativa.
- Manejo explícito de `recovered`, `already_terminal` y rechazos concurrentes.

## Exclusiones

No se agregan reglas stale/eligibility, RPC, migration, repository recovery,
sync, retry, resume, abort, provider calls, OAuth, reconnect, refresh, remoto
funcional ni cierre Git.

## Diseño

Una columna Actions compone un único dialog/form por fila elegible. El cliente
envía sólo run ID, target terminal y reason al POST 2.20U; el servidor vuelve a
autenticar, autorizar y resolver tenant mediante `hub_memberships`. El éxito o
estado concurrente invalida la key de listado; ningún error backend raw llega
al toast.

## Validaciones

Tests focalizados UI/mutation 69/69 PASS, suite completa 232/232 PASS,
typecheck PASS y lint PASS sin warnings. Build, Supabase reset y recovery real
quedaron fuera.

## Checkpoint

Implementación y validación local completas, sin cierre Git. El working tree
conserva 2.20V-A y no hubo remoto, provider calls, recovery real ni acciones
Git.

## Remote UI validation autorizada

La validación remota queda autorizada exclusivamente con fixtures sintéticos
tenant-bound y cleanup completo. No se usarán runs, Stores, Connections,
Listings o credenciales reales; provider calls, OAuth, refresh, reconnect y
listing sync permanecen prohibidos. El baseline local es 69/69 focalizados,
232/232 suite, typecheck y lint PASS.

## Investigación focalizada de feedback toast

Se abre una auditoría local y visual acotada para determinar si la falta de

## Resultado de la investigación de toast

Causa clasificada como `AUTOMATION_OBSERVABILITY_LIMITATION`. Ambos outcomes
de recovery invocan feedback Sonner seguro, el `Toaster` único está montado en
el root layout y la dependencia está presente y resoluble. Un disparador local
existente confirmó en Chrome que el toast global aparece y es visible; no se
encontró defecto de código, mount, portal, CSS o z-index.

No se modificó código ni se repitieron tests, typecheck o lint. La evidencia
local ya validada, el flujo remoto funcional (mutation, invalidación, refresh y
action removal) y la comprobación visual del Toaster permiten considerar el
feedback validado sin adaptar producción a la herramienta. Remote validation
adicional y fixtures: N-A; fixtures restantes: cero; provider calls: cero.
