# Fase 2 — Decisiones posteriores a auditoría 2.0

Status: **APPROVED**

## Purpose

Resolver las decisiones bloqueantes antes de la Subfase 2.1. La auditoría y diseño 2.0 están completados; este mandato no autoriza implementar 2.1.

## Decisions

- `hub_memberships` es la fuente server-side definitiva del rol e-Hub por Organization. Clerk conserva Authentication, sesión, `userId`, Organization activa y membership técnica. El mapping `org:admin -> Owner` / `org:member -> Employee` de Fase 1 es transitorio y no será fallback permanente.
- Si una Organization no tiene Owner en `hub_memberships`, un Clerk `org:admin` autenticado puede ejecutar un bootstrap server-side para crear el primer Owner. Una vez creado, el bootstrap queda cerrado y otros admins de Clerk no reciben Owner automáticamente.
- Owner y Manager tienen Store Scope implícito sobre todas las Stores de su Organization, sin `store_assignments`; siguen requiriendo permissions. Employee y Client requieren assignments explícitos; sin membership o assignment, deny. Client no necesita tabla propia mientras sea una membership `Client` con assignments.
- Permission y Store Scope son controles independientes: `Authentication -> Organization -> hub_membership -> Role -> Permission -> Store Scope -> Resource Scope -> Operation`.
- Store tiene relación 1:N con Connections. `provider + external_account_id` es único entre conexiones activas cuando existe account ID. Una transferencia futura requiere disconnect/disable/release y nueva autorización; nunca se cambia arbitrariamente Store u Organization de una Connection activa.
- Provider permanece como conjunto controlado (`IntegrationProvider`) y la base usará un constraint equivalente; no habrá tabla `providers`.
- Las migraciones serán SQL versionado en `supabase/migrations/` mediante Supabase CLI, con pinning/ejecución reproducible a auditar en 2.1. No se introduce ORM ni nueva librería runtime de DB.
- Tenant isolation primario: backend server-only, repositories/queries tenant-scoped y FKs/constraints. RLS queda diferido como defensa adicional, porque la service role actual no es una garantía de aislamiento.
- Se aprueba como base conceptual `hub_memberships`, `stores`, `store_assignments` y `connections`; `organization_id` puede duplicarse de forma controlada para FKs compuestas multi-tenant.
- Connections no almacenará secretos OAuth en campos expuestos. Tokens, cifrado, key version y expiry confidencial se diseñan en Fase 3. `StoreIntegrationResolver` permanece diferido hasta que haya adapter real.
- `created_at` y `updated_at` son necesarios; `created_by`, `updated_by`, audit log general y `deleted_at` se difieren. Preferir status controlado a borrar integración activa.
- Secuencia provisional: 2.1 decisiones finales de schema y convención de migraciones; 2.2 schema mínimo; 2.3 repositories + fuente propia de roles; 2.4 Store Scope; 2.5 Connections sin OAuth; 2.6 checkpoint. Ajustes solo se reportan antes de implementar.

## Restrictions

No crear `supabase/`, tablas, migraciones, repositories, endpoints, bootstrap, Store Scope, OAuth ni StoreIntegrationResolver. No modificar `package.json`, instalar Supabase CLI ni otras dependencias, eliminar el mapping de Fase 1, cambiar código funcional, hacer `git add`, commit o push.

## Prompt

### Fase 2 — resolución de decisiones de diseño post-2.0

Proyecto: e-ngenieria Hub. Rama: `develop`. Commit base: `7b697b9`. Fase 1 cerrada. La auditoría y diseño de 2.0 están completados. Este mandato resuelve decisiones bloqueantes antes de 2.1 y solo autoriza registrarlas como documentación.

No implementar 2.1, no crear tablas, migraciones, `supabase/`, repositories, endpoints, bootstrap, Store Scope, OAuth ni StoreIntegrationResolver. No instalar dependencias, modificar código funcional o `package.json`, eliminar aún el mapping de Fase 1, ni ejecutar `git add`, commit o push.

1. Aprobar `hub_memberships` como fuente server-side definitiva de Owner, Manager, Employee y Client dentro de una Organization. Clerk continúa con Authentication, sesión, identidad, Organization activa y membership técnica; `org:admin` y `org:member` no son la fuente permanente de roles e-Hub.
2. Aprobar bootstrap controlado: solo cuando una Organization no tiene Owner en `hub_memberships`, un usuario autenticado `org:admin` puede crear el primer Owner. Luego el bootstrap se cierra; nuevos admins Clerk no obtienen Owner automáticamente y los roles posteriores usan autorización interna.
3. Aprobar Owner con Store Scope implícito para todas las Stores de su Organization, sin assignments, pero siempre sujeto a Permission checks.
4. Aprobar Manager con Store Scope implícito para todas las Stores de su Organization, sin assignments y sin equivaler a Owner. Scope global no concede permissions ausentes.
5. Aprobar Employee con `store_assignments` explícitos; puede tener 0, 1 o N Stores y sin assignment queda deny.
6. Aprobar Client como `hub_membership` con rol Client más assignments explícitos. Puede tener una o varias Stores; no crear tabla `clients` hasta que exista una entidad comercial independiente.
7. Aprobar la matriz: Owner y Manager todas las Stores de la Organization; Employee y Client solo Stores asignadas; rol desconocido o sin membership, deny, salvo bootstrap específico del primer Owner.
8. Registrar que Permission y Store Scope son independientes: `Authentication -> Organization -> hub_membership -> Role -> Permission -> Store Scope -> Resource Scope -> Operation`.
9. Registrar que `storeId` en URL, body, query o header solo identifica el recurso solicitado. El servidor debe comprobar identidad, Organization, membership, assignment cuando corresponda y default deny.
10. Aprobar `Store 1:N Connections` para soportar multicanal y potencialmente varias cuentas del mismo provider cuando exista caso real; Store no equivale a cuenta externa.
11. Aprobar unicidad inicial de `provider + external_account_id` entre conexiones activas, solo si existe account ID, mediante índice parcial o equivalente PostgreSQL.
12. Diferir transferencia: una cuenta externa solo podrá cambiar de Store u Organization mediante workflow explícito de disconnect/disable/release y nueva connect/authorize; nunca mediante UPDATE arbitrario de una Connection activa.
13. Mantener `IntegrationProvider` como conjunto controlado y exigir constraint equivalente en base; no crear tabla `providers`.
14. Aprobar SQL migrations + Supabase CLI en `supabase/migrations/`, versionadas y reproducibles. 2.1 debe decidir pinning/ejecución exactos; preferir proyecto/CI reproducible a instalación global. No introducir ORM solo para migraciones.
15. Mantener `@supabase/supabase-js` existente y no introducir Prisma, Drizzle, TypeORM ni Sequelize sin nueva aprobación.
16. Aprobar tenant isolation primario mediante backend server-only, repositories/queries tenant-scoped y constraints relacionales. Toda query recibe `organizationId` desde contexto server-side y las mutaciones incluyen el tenant en su predicado.
17. Diferir RLS: service role no es garantía de aislamiento. Solo evaluar RLS cuando exista propagación Clerk/PostgreSQL compatible y probada sin depender del bypass de service role.
18. Aprobar `organization_id` duplicado de forma controlada donde permita FKs compuestas: assignments relacionan `(membership_id, organization_id)` y `(store_id, organization_id)`; Connections relacionan `(store_id, organization_id)`.
19. Aprobar como base conceptual `hub_memberships`, `stores`, `store_assignments` y `connections`; 2.1 define el schema mínimo exacto y no agrega tablas sin justificación.
20. Prohibir secretos OAuth en campos expuestos de Connections. Fase 3 definirá almacenamiento confidencial separado o equivalente para tokens, key version y expiry metadata, todo server-only.
21. Diferir StoreIntegrationResolver: Fase 2 deja Store, Connection y provider disponibles; el resolver aparece cuando exista adapter funcional real.
22. Exigir `created_at` y `updated_at`; diferir `created_by`, `updated_by` y audit log general. Revisar trazabilidad antes de mutaciones administrativas sensibles sobre roles o assignments.
23. No crear `deleted_at` por costumbre. Usar status controlado cuando corresponda y preferir deshabilitar a borrar información de integraciones activas; política exacta diferida.
24. Adoptar provisionalmente: 2.1 decisiones finales de schema y convención de migraciones; 2.2 schema mínimo; 2.3 repositories server-only y roles propios; 2.4 Store Scope; 2.5 Connections sin OAuth; 2.6 checkpoint. Ajustes deben reportarse antes de implementar.
25. Persistir estas decisiones prioritariamente en handoff, plan y multi-tenancy, sin reescribir documentos completos ni duplicar contenido.
26. Archivar este mandato en `docs/prompts/phase-02/2.0-decisions.md` con Status, Purpose, Decisions, Restrictions, Prompt completo, Result y Commit pendiente.
27. Tras cambios documentales, ejecutar únicamente `git diff`, `git diff --check` y `git status --short`; no hace falta build si no hay código.
28. El checkpoint debe confirmar decisiones, archivos, diff/check, estado Git y que no hubo código, dependencias, tablas, migraciones, OAuth, inicio de 2.1 ni operaciones Git de escritura.
