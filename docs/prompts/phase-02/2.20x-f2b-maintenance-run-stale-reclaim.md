# Fase 2.20X-F2b — Maintenance run stale reclaim

Fecha: 2026-08-28. Estado: **LOCAL IMPLEMENTATION + VALIDATION PASS**.

## Problema e invariantes

Un hard crash entre start y finalize puede dejar un maintenance run `running`
y bloquear su Connection. El reclaim debe conservar scope, counters y evidencia,
terminalizar de forma idempotente y no tocar eventos, leases, Listings ni
provider.

## Stale threshold

La evidencia durable es `last_checkpoint_at`. Un run es stale cuando continúa
`running` y su último checkpoint tiene al menos diez minutos. El margen supera
ampliamente el budget normal de 45 segundos y absorbe latencia de provider, DB,
runtime y solapamientos sin permitir al caller elegir el cutoff.

## Checkpoints y reclaim

No se introduce heartbeat loop. El servicio actualizará un checkpoint sólo en
puntos naturales de progreso con counters monotónicos y continuación de missed
feeds. Una RPC server-only bloqueará la fila, comprobará el threshold calculado
en DB y cambiará un stale run a `failed` con
`maintenance_stale_reclaimed`. Dos reclaimers quedan serializados; el segundo
observa un run terminal y no repite efectos.

El orquestador podrá reclamar el run devuelto como `already_running` y reintentar
start una sola vez. Los leases/CAS X-D siguen siendo la única autoridad por
evento y expiran con su semántica existente.

## Exclusiones

No scheduler, cron, route HTTP, deployment, UI nueva, audit system nuevo,
provider real, remote apply ni cierre Git.
