# Fase 2.20X-A — Incremental sync & notifications design audit

Fecha: 2026-08-28. Estado: **AUDIT COMPLETED**. Este documento es historial
operativo; el repositorio y la documentación técnica vigente son la fuente de
verdad. 2.20W permanece cerrado. X-A no implementa runtime, schema ni provider
calls.

## Objetivo y fuentes

Diseñar la actualización incremental de Listings posterior al full scan y la
reconciliation segura de 2.20W, sin convertir una notification en dato
autoritativo ni debilitar Organization, Store o Connection scope.

Se contrastaron el listing client, backfill service, run orchestration,
repositories, recovery/admin UI y migrations T/U/W con documentación oficial
vigente de Mercado Libre:

- [Notificaciones](https://developers.mercadolibre.com.ar/es_ar/descripcion-de-articulos/productos-recibe-notificaciones)
- [Seguridad de aplicaciones](https://developers.mercadolibre.com.ar/es_ar/descripcion-de-articulos/seguridad-apps)
- [Seguridad en integraciones](https://developers.mercadolibre.com.ar/es_mx/seguridad-desarrollo-seguro)
- [Sincronización y estados de publicaciones](https://developers.mercadolibre.com.ar/es_ar/administra-areas-de-cobertura/producto-sincroniza-modifica-publicaciones)

## Findings del flujo vigente

Son reutilizables:

- resolución y validación server-only de Connection activa y credenciales;
- `MercadoLibreListingsClient.getListingDetails`, que consulta `/items` en
  batches de hasta 20 y normaliza status, cantidades, precio, moneda y
  `date_created`/`last_updated`;
- timeout de 15 segundos, hasta tres intentos para red, timeout, `429` y `5xx`,
  `Retry-After`, backoff exponencial y jitter;
- `ExternalListingSummary`, el mapper y el upsert idempotente por
  `(connection_id, external_listing_id)`;
- Store/Connection scope, errores sanitizados y admin read model agregable.

No deben reutilizarse como event queue:

- `listing_sync_runs`, cuyo único kind es `listing_backfill`, exige actor y
  modela un scan completo con checkpoints y reconciliation;
- `audit_events`, que exige actor membership y no modela claim, retry ni
  procesamiento asíncrono;
- recovery 2.20U, que terminaliza stale runs pero no reanuda trabajo;
- la UI 2.20V, que sólo administra runs de backfill.

## Contrato oficial observado

Para topic `items`, Mercado Libre envía un HTTP POST con `resource` como
`/items/{ITEM_ID}`, `user_id`, `topic`, `application_id`, `attempts`, `sent` y
`received`; la estructura general actual también muestra `_id`, pero ejemplos
históricos de `items` no permiten asumir que siempre esté presente. El detalle
canónico se obtiene con `GET /items/{ITEM_ID}`.

El receptor debe responder HTTP 200 rápidamente; la guía de seguridad fija
menos de 500 ms y recomienda persistir/encolar antes del ACK. Sin HTTP 200 hay
reintentos; la documentación describe ocho intentos durante una hora y luego
la notification como perdida. `missed_feeds` conserva esas notificaciones hasta
dos días; para topic `items` exige una consulta separada con `site_id` por sitio.
No hay garantía oficial encontrada de entrega exactly-once ni de orden.

La documentación de seguridad recomienda HTTPS, defensa por IP, HMAC-SHA256,
idempotencia y consultar el recurso oficial. Sin embargo, las páginas revisadas
no publican un contrato concreto y estable de header, canonical string o
derivación del secreto HMAC. **DECISIÓN PENDIENTE:** confirmar ese contrato en la
configuración/documentación oficial antes de exponer un callback productivo; no
inventarlo ni tratar una allowlist de IP como autenticación suficiente.

## Flujo canónico ajustado

La secuencia propuesta separa intake de processing:

```text
HTTP notification
  → validar transporte, tamaño, schema, topic y application_id
  → resolver Connection por provider + user_id
  → deduplicar y persistir el evento en forma durable
  → responder HTTP 200 en menos de 500 ms
  → worker reclama el evento
  → obtiene credencial server-only
  → GET del resource oficial
  → normaliza
  → aplica protección de frescura e upsert tenant-scoped
  → terminaliza el evento
```

La notification nunca es source of truth. `organization_id`, `store_id`,
`connection_id`, role o permission del request no participan como autoridad.
`application_id` debe coincidir con la aplicación propia configurada y
`String(user_id)` resuelve la única Connection por
`provider='mercado-libre' + external_account_id`; nickname no participa.

Un fallo transitorio antes de persistir devuelve no-200 para permitir retry. Un
payload inválido, otra aplicación o una cuenta no vinculada falla cerrado, no
produce trabajo ni revela si existe un tenant. La política HTTP exacta para esos
rechazos se fija junto con el contrato de autenticidad antes del callback.

## Idempotencia, orden y concurrencia

La clave canónica de deduplicación es:

1. `provider + application_id + _id` cuando `_id` válido está presente;
2. en su ausencia, SHA-256 de una serialización canónica de
   `provider|topic|application_id|user_id|resource|sent`.

`attempts` y `received` no integran la clave porque cambian entre entregas. Un
UUID local puede identificar la fila, pero no deduplicar el evento externo. La
unicidad se impone en DB y un duplicate delivery devuelve el mismo resultado de
intake sin encolar trabajo adicional.

`sent` ordena observabilidad, no autoriza un overwrite. El worker siempre hace
GET y la persistencia compara atómicamente `provider_updated_at`:

- mayor que el valor almacenado: aplicar la lectura positiva;
- menor: no-op stale;
- igual con datos equivalentes: no-op idempotente;
- igual con datos distintos, o timestamp ausente: no sobrescribir; clasificar
  como evidencia ambigua/retryable y dejar el full scan como safety net.

El claim del evento necesita lease/CAS. Dos workers o dos notifications del
mismo item pueden hacer GET, pero sólo la escritura con evidencia más nueva
puede ganar. No se mantiene una transacción DB durante HTTP.

## Interacción con status y reconciliation

Una respuesta positiva y válida de `/items/{id}` sí puede actualizar el status
observado del provider y los demás campos normalizados. Una notification o un
404 por sí solos nunca implican `deleted`, `closed`, `removed` ni
`confirmed_missing`; un not-found se registra con error seguro y queda para
retry/full scan según su clasificación.

Una lectura positiva incremental fresca puede revertir
`missing_candidate → seen`, limpiar `not_seen_since` y llevar
`consecutive_not_seen_count` a cero. No cambia `last_seen_sync_run_id`: ese campo
continúa significando el último full scan que observó la fila y no se inventa un
run inexistente. Tampoco incrementa `listing_sync_runs.reappeared_count`, porque
no pertenece a un backfill. La futura persistencia incremental debe ser una
primitive atómica separada de `persist_listing_sync_batch_for_run`.

El full scan periódico conserva tres responsabilidades: descubrir altas que no
llegaron por notification, reparar pérdida o backlog mayor a dos días y producir
evidencia de completitud para reconciliation. Sólo un run
`listing_backfill` técnicamente completo y elegible puede crear
`missing_candidate`.

## Modelo de ejecución y retries

Recomendación: **hybrid**.

- Notifications: entidad durable y worker separados, sin crear
  `listing_sync_run` por item.
- Full scans: conservan `listing_sync_runs`, checkpoints, single-running,
  recovery y reconciliation existentes.
- Request path: valida, persiste/deduplica y responde; no descifra credenciales
  ni llama al provider.
- Worker: claim con lease, GET canónico, normalización y persistencia.
- Retry worker: reintenta red, timeout, `429`, `5xx` y DB temporal con backoff,
  jitter y `Retry-After`; errores contractuales/4xx no retryable terminan de
  forma segura.
- Scheduler futuro: consulta `missed_feeds` dentro de su ventana y dispara full
  scans periódicos. No se implementa en X-B.

No se justifica una DLQ separada todavía: un estado terminal `failed` con error
allowlisted y replay administrativo futuro es suficiente hasta medir volumen.

## Decisión de schema

**SCHEMA_EXTENSION_REQUIRED.** El schema actual no puede hacer ACK durable,
dedupe externo, claim, retry ni observabilidad de backlog sin deformar
`listing_sync_runs`.

Tabla propuesta: `integration_events`, provider-agnostic y server-only.

- identidad/scope: `id uuid`, `provider`, `application_id`, `organization_id`,
  `store_id`, `connection_id`;
- envelope normalizado: `topic`, `resource`, `external_resource_id`,
  `external_event_id nullable`, `deduplication_key` SHA-256;
- tiempos: `provider_sent_at`, `provider_received_at nullable`, `received_at`,
  `processed_at nullable`, `created_at`, `updated_at`;
- estado: `pending|processing|retrying|processed|failed|ignored`;
- ejecución: `delivery_attempts`, `processing_attempts`, `next_attempt_at`,
  `processing_lease_id`, `processing_lease_expires_at`;
- error seguro: `error_code nullable`, allowlisted y sin summary libre.

No se guarda raw payload, headers, firma, access token, ciphertext ni respuesta
raw del provider. La tabla requiere:

- FK compuesta a la misma Organization/Store/Connection y consistencia de
  provider reforzada por constraint/clave compuesta;
- unique `(provider, application_id, deduplication_key)`;
- checks de coherencia entre status, lease, attempts y timestamps;
- índice parcial por `(status, next_attempt_at)` para `pending|retrying` e índice
  `(organization_id, connection_id, received_at desc)`;
- RLS deny-by-default, cero policies browser-facing y DML/RPC sólo para
  `service_role`;
- RPCs atómicas futuras de intake/dedupe, claim y complete/retry, todas scoped y
  con EXECUTE revocado a PUBLIC/anon/authenticated.

La tabla es multi-provider sin inventar un payload universal: conserva un
envelope pequeño común y cada adapter valida/normaliza su webhook antes del
intake. Los detalles de autenticidad, topics y resource parsing permanecen en
`src/integrations/{provider}`.

## Scope exacto propuesto para 2.20X-B

**2.20X-B — Event Intake Foundation**:

1. migration local de `integration_events`, constraints, índices, RLS/grants y
   RPC atómica de dedupe/intake;
2. repository server-only y modelos provider-agnostic del envelope;
3. parser/normalizador puro para notification `items`, con límites de tamaño,
   allowlists, extracción estricta del item ID y dedupe key determinista;
4. resolver server-only `provider + external_account_id` que devuelve el scope
   persistido sin aceptar tenant IDs del caller;
5. tests SQL/TypeScript de duplicados, cross-scope, payload inválido, `_id`
   presente/ausente, application mismatch y ausencia de material sensible.

X-B no expone todavía un callback público, no llama Mercado Libre, no procesa
items, no implementa worker/retries, no toca Listings ni crea sync runs. El
callback queda detrás del gate pendiente del contrato oficial de autenticidad.

Subfases posteriores propuestas:

- X-C: callback seguro + ACK durable una vez resuelto el contrato de
  autenticidad;
- X-D: worker de item fetch, freshness CAS y persistencia/reappearance positiva;
- X-E: retry/replay y recuperación `missed_feeds` por site;
- X-F: scheduler de full scans y observabilidad administrativa mínima.

## Riesgos y preguntas abiertas

- contrato concreto de firma HMAC/header/secret no confirmado en la referencia
  oficial revisada;
- wording oficial distinto entre “lost after eight attempts” y “notifications
  disabled”; no depender de retries ilimitados;
- confirmar credencial/autorización exacta para `missed_feeds` y operación por
  múltiples `site_id` antes de X-E;
- definir retención/particionado sólo después de observar volumen real;
- timestamps iguales o ausentes deben permanecer fail-closed hasta una
  estrategia de versión provider comprobable;
- la allowlist de IP cambia y sólo puede ser defensa adicional, no identidad
  única.
