# Fase 2.20X-F3-B2 — Auditoría de renombre de producto

Fecha: 2026-08-31. Estado: **AUDITORÍA COMPLETADA**.

## Objetivo

Auditar, sin ejecutar el renombre, la transición de `e-ngenieria Hub` /
`e-ngenieria-hub` a **Pimienta Hub** / `pimienta-hub` antes del gate remoto
F3-C.

## Alcance

La revisión cubre branding activo, identificadores de proyecto, documentación,
Docker, Supabase local/remoto, GitHub, Clerk, Mercado Libre Developers, Sentry,
Coolify, VPS y dominio/DNS. Cada referencia se clasifica como
`CHANGE_REQUIRED`, `CHANGE_RECOMMENDED`, `REVIEW_MANUALLY`,
`PRESERVE_HISTORICAL`, `PRESERVE_TECHNICAL` o `EXTERNAL_CHANGE`.

No se renombra código, carpeta, repository, recurso externo, migration ni
contrato técnico. Los prompts previos y el historial Git se preservan.

## Findings y plan recomendado

El inventario encontró 140 referencias nominales: 120 ocurrencias directas de
`e-ngenieria`/`e-Hub` en 51 archivos, 17 referencias activas al branding del
starter y tres ubicaciones nominales fuera del contenido de archivos (`origin`,
carpeta local y directorio de skill). Clasificación:

| Categoría | Cantidad | Criterio |
| --- | ---: | --- |
| `CHANGE_REQUIRED` | 57 | Branding activo, metadata, package/lock y CTA del repository. |
| `CHANGE_RECOMMENDED` | 3 | `project_id` local, carpeta de trabajo y directorio de skill. |
| `REVIEW_MANUALLY` | 3 | Asset OpenGraph y sus dos referencias; falta definir asset Pimienta. |
| `PRESERVE_HISTORICAL` | 75 | 71 menciones en prompts, tres en el audit inicial de Cursor y una en `README_OLD.md`. |
| `PRESERVE_TECHNICAL` | 1 | Comentario de una migration histórica; la migration no se edita. |
| `EXTERNAL_CHANGE` | 1 | URL actual de `origin`; se cambia después del rename en GitHub. |

Los archivos activos alcanzados son README, AGENTS, REGLAS, plan, handoff,
deployment, documentación técnica que usa el nombre de producto, siete archivos
de skills locales, `package.json`, `bun.lock`, layouts/metadata, CTA GitHub,
asset OpenGraph y `supabase/config.toml`. No existe manifest, email/template ni
texto de marca propio en sidebar/header/auth; hoy esas superficies usan
Organization de Clerk o textos genéricos. La metadata pública todavía muestra
“Shadcn Dashboard”.

`package.json` debe adoptar `pimienta-hub`; `bun.lock` debe actualizar sólo la
metadata del workspace para conservar consistencia. No se renombra ninguna env
var, tabla, columna, RPC, constraint, index, enum, `hub_memberships`,
`HubMembership`, `HubRoleSource` ni helpers `resolve*HubRole`.

La carpeta local no gobierna por sí sola los containers: `supabase/config.toml`
fija explícitamente el `project_id`. Cambiarlo crea otro namespace local y puede
dejar el stack/volúmenes anteriores separados; por eso requiere backup, stop y
una decisión explícita, nunca reset o delete incidental.

## Plan recomendado

1. **R1 — repo y branding activo.** Cambiar nombre de package/lock, metadata,
   CTA, docs canónicas y skills; decidir/reemplazar el asset OpenGraph. Rollback:
   revertir un único diff de rename.
2. **R2 — workspace local.** Conservar o migrar deliberadamente el `project_id`,
   detener el stack local si corresponde, renombrar carpeta y reabrir VS Code.
   Rollback: volver al path y `project_id` previos sin borrar volumes.
3. **R3 — GitHub y dashboards.** Decidir dominio, renombrar repo/origin, branding
   Clerk, URLs Clerk/ML y Sentry opcional. Credenciales, Organizations,
   memberships y provider identity se preservan. Rollback: restaurar nombres y
   últimas URLs válidas.
4. **R4 — validación local.** Install frozen, tests, typecheck, lint, build,
   Docker/health y verificación del stack Supabase, sin OAuth real salvo un gate
   posterior explícito.
5. **R5 — F3-C.** Aplicar migrations por el gate ya definido, desplegar en
   Coolify, validar health/TLS/callbacks y recién entonces habilitar scheduler.

El rename debe ocurrir **antes de F3-C** para no configurar dos veces Coolify,
Clerk y Mercado Libre. El dominio definitivo y el asset de marca siguen como
decisiones pendientes; por eso el resultado es `RENAME_DECISIONS_REQUIRED`.

Riesgos: runtime bajo, auth medio, OAuth alto si cambia el host, database bajo,
deploy medio, Git medio, documentación baja y entorno local medio. Migrations
afectadas: cero. 2.20Y i18n permanece después del cierre de 2.20X, con
`es-419` principal, `pt-BR` soportado y fallback `en`.
