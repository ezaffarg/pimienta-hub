# FASE 2 — 2.20S Listing Sync Production Hardening

Base `067a57530162296afc0415136ccc829a6f112ae2`. 2.20E, 2.20P,
2.20Q y 2.20R están cerradas; el primer listing sync real y su idempotencia
pasaron con una publicación persistida, Connection activa y
`credential_version=2`.

Este turno autoriza únicamente auditar la capacidad actual del listing sync y
clasificarla como `IMPLEMENTED`, `PARTIAL` o `MISSING`. El alcance se limita a
discovery oficial, paginación, multiget/detail, normalización, sync,
repository/schema de listings, tests y documentación relacionada. OAuth,
autorización y RBAC sólo se consideran cuando sean dependencia directa.

No se autoriza modificar código, crear migrations, escribir en DB, llamar a
Mercado Libre, ejecutar listing sync, OAuth, reconnect o refresh, ni realizar
cierre Git. El resultado debe identificar el cambio mínimo de mayor valor para
operación real, sus riesgos, necesidad de migration, código y tests, sin
implementar todavía.

## Result

Auditoría completada sin ejecutar Mercado Libre, refresh, sync ni escrituras de
DB. La foundation actual implementa multiget acotado, normalización canónica,
upsert idempotente, actualización de campos observables, timestamp local y
binding Organization/Store/Connection. El runtime de listings consume
`MercadoLibreCredentialService.getValidAccessToken()`.

La capacidad sigue siendo parcial para operación real: el cliente calcula un
offset siguiente, pero el service no acepta cursor ni recorre páginas; no hay
scan para más de 1000 IDs, orquestador, manejo visible de fallos parciales,
retry/backoff/429, métricas, audit de sync, detección de ausentes o semántica
local inactive. El batch actual cubre sólo una página de hasta 20 IDs. Los
campos `provider_created_at` y `provider_updated_at` existen en schema, pero no
cruzan contrato, mapper ni repository.

La propuesta mínima para 2.20S es extender el flujo existente con un backfill
server-only paginado/scan, multiget en chunks de 20, resultado estructurado de
errores parciales, retry acotado con backoff+jitter para 429/5xx, upsert por
batch y resumen seguro de métricas. También debe poblar los dos timestamps de
provider ya existentes. No debe marcar ausentes ni agregar lifecycle local en
este corte: eso requiere un sync-run completo y una decisión posterior.

No se necesita migration para esta propuesta mínima; sí cambios focalizados en
contrato canónico, client/service de listings, repository y tests. Estado:
`READY_TO_IMPLEMENT_2_20S`.

## Implementación

Autorizada únicamente en local sobre la misma subfase. El cambio debe reutilizar
el runtime server-only actual para discovery completo con offset/scan, details
en chunks de hasta 20, fallos parciales sanitizados, timeout y retries acotados
con backoff/jitter, timestamps oficiales del provider y resultado agregado de
persistencia. Se conservan binding e idempotencia existentes.

Quedan fuera lifecycle por ausencia, soft-delete, variaciones, User Products,
métricas o audit persistentes, nuevas migrations, llamadas reales, remoto,
OAuth, refresh, reconnect y cierre Git. Resultado de implementación: COMPLETED.

### Resultado local

El cliente separa discovery y details, recorre offset/limit hasta el límite
normal y cambia a scan/scroll cuando el total supera 1000. El service deduplica
IDs, procesa secuencialmente chunks de hasta 20 y persiste cada conjunto válido
mediante `ListingSyncService`. Devuelve conteos seguros de descubiertos,
solicitados, recuperados, persistidos y fallidos, con errores parciales por
external listing ID sin token, headers ni bodies.

Las requests abortan a los 15 segundos y tienen hasta 3 intentos para timeout,
red, 429 y 5xx. El backoff exponencial usa jitter y respeta `Retry-After`; 4xx
no recuperables y respuestas inválidas no se reintentan. `date_created` y
`last_updated` alimentan los timestamps nullable del provider ya existentes;
active, paused y closed conservan el status textual.

Tests focalizados 19/19, suite completa 150/150, typecheck y lint: PASS. No hubo
build, migration, DB reset/remoto, llamadas reales, sync real, OAuth, refresh,
reconnect ni cierre Git. Resultado: `2_20S_LOCAL_PASS`. Recomendación:
`READY_FOR_REAL_BACKFILL_VALIDATION`.

## Validación real controlada

El precheck remoto read-only confirmó una Store, una Connection Mercado Libre
activa y tenant-bound, un `integration_secret`, `credential_version=2`, lease
libre, un Listing y cero duplicados. El access token persistido seguía vigente,
por lo que no se ejecutó refresh, OAuth ni reconnect.

El backfill productivo completo se ejecutó dos veces contra endpoints oficiales
read-only. En cada pasada recorrió una página sin scan, descubrió, solicitó,
recuperó y persistió un listing en un batch; hubo cero fallos parciales, retries,
respuestas con `Retry-After` y timeouts. Ambas pasadas reutilizaron el mismo
Listing: el conteo permaneció en uno, los external IDs se mantuvieron estables,
los bindings de Store y Connection pasaron y no aparecieron duplicados.

La respuesta real entregó `date_created` y `last_updated`; el mapper los
persistió en `provider_created_at` y `provider_updated_at`. El postcheck
normalizado confirmó también status, cantidades, precio/moneda, listing type,
condition, permalink y thumbnail cuando existe. La representación runtime de
PostgreSQL/Supabase para `numeric` y timestamps requirió comparar por valor y no
por identidad textual; no hubo pérdida de datos.

Estado final: Listings 1, duplicados 0, `credential_version=2` y lease libre.
No hubo escrituras hacia Mercado Libre, migration, cambio de schema, cambio de
código productivo ni cierre Git. Resultado: `REAL_BACKFILL_2_20S_SUCCESS`.
Recomendación: `READY_TO_CLOSE_2_20S`.
