# FASE 2 — 2.16 OAUTH SECURITY + CONNECTION/AUDIT FOUNDATIONS

Implementación técnica controlada. No ejecutar OAuth real ni crear Stores/Connections reales.

Base: `f465e7a` en `develop`. Estado: Owner persistente único; Stores, Connections y Assignments en cero; Mercado Libre primary provider; OAuth NOT STARTED; fallback Clerk TRANSITIONAL.

## Objetivo

Implementar exclusivamente foundations para que OAuth futuro de Mercado Libre sea seguro, sin botón, authorize redirect, callback, token exchange, `GET /users/me`, refresh, webhooks ni sync.

## Decisiones canónicas

- Owner y Manager pueden conectar/reconectar providers; Employee no; Client sólo self-onboarding/reconnect propio.
- La identidad ML será `GET /users/me` → `id` → `external_account_id`; Store.name no es identidad.
- Connection disabled se reactiva; no se duplica identidad histórica; cross-tenant reassignment automático se deniega.
- Store + Connection y Client Store + Connection + assignment deben ser atómicos/coherentes.
- Audit Log: Owner/Manager read; Employee/Client deny.
- Tokens server-only y fuera de `connections`; MercadoCuentas no es dependencia runtime.

## Foundations requeridas

1. Nueva migration local si es necesaria para `oauth_attempts`, `integration_secrets`, `audit_events`, unicidad definitiva de Connection y primitives de onboarding.
2. `oauth_attempts`: UUID, Organization, actor membership, provider/purpose allowlisted, digest seguro de state, verifier protegido si PKCE, expiración, consumo único y timestamps. State aleatorio, opaco, expirable, tenant/actor-bound.
3. `integration_secrets` 1:1 con Connection, tokens cifrados, expiración, metadata mínima, timestamps y versionado de clave razonable. Nunca plaintext ni secretos en `connections`.
4. Cifrado application-level server-only con clave maestra de variable de entorno, primitive estándar autenticada y sin clave en DB/Git/browser. Documentar sólo el nombre en `env.example.txt`.
5. Unicidad `provider + external_account_id` también para disabled. Antes de migrar, comprobar remoto read-only `connections = 0`; si hay filas, detenerse.
6. Primitive tenant-safe de reactivación que preserva la Store y falla cerrado cross-tenant.
7. Primitive DB-backed y concurrente para onboarding administrativo: Store + Connection. Otra para Client: Store + Connection + assignment, validando membership Client del mismo tenant. Outcomes controlados: created, already_connected, reactivatable/conflict o equivalente.
8. `audit_events` con actor, Organization, Store opcional, acción, recurso, metadata JSON controlado/sanitizado y timestamps. Convención: `integration.connected`, `integration.reconnected`, `integration.disconnected`, `store.created`, `membership.assigned`, `listing.updated`, `question.answered`, `export.generated`.
9. RBAC server-side: `audit:read`, `integration:connect`, `integration:reconnect` y capability contextual Client `integration:self_connect`, sin permiso global de Connections para Client.
10. Services server-only previstos: create/consume OAuth attempt, store/read encrypted credentials, admin/client onboarding, reactivation y audit write. Sin rutas OAuth.
11. Zod strict, allowlists, límites, UUID/provider/status validation y sin mass assignment. Errores/logs no exponen ciphertext, plaintext ni tokens.

Aplicar migration sólo localmente, validar constraints/transacciones en Postgres local; no `db push` remoto. Ejecutar tests relevantes, typecheck, lint, build si corresponde, `git diff --check`, status y diff.

## Restricciones

No aplicar migration ni escribir datos en remoto; no crear Stores/Connections/attempts/secrets/audit remotos; no OAuth real ni rutas, callbacks, token exchange, refresh, disconnect API, webhooks, sync, UI, export/audit UI, cambios de Clerk o fallback removal. No `git add`, `commit` ni `push` hasta checkpoint.
