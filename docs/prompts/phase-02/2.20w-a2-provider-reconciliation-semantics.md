# Fase 2.20W-A2 — Provider reconciliation semantics

## Objetivo y alcance

Resolver con documentación oficial de Mercado Libre qué puede afirmarse sobre
search, scan, estados, ausencia y notificaciones para limitar 2.20W-B a evidencia
interna reversible. Este bloque no modifica código, schema, tests ni recursos
locales o remotos fuera de este prompt.

Ver [2.20W-A](./2.20w-a-listing-reconciliation-design-schema-audit.md) para el
audit de schema y flujo local; este documento registra sólo la resolución
provider-specific complementaria.

## Fuentes, hechos y contrato

### Fuentes oficiales

- [Ítems y Búsquedas](https://developers.mercadolibre.com.ar/es_ar/api-docs-es/items-y-busquedas)
- [Flujo y estados de las publicaciones](https://developers.mercadolibre.com.ar/es_ar/administra-areas-de-cobertura/producto-sincroniza-modifica-publicaciones)
- [Notificaciones](https://developers.mercadolibre.com.ar/es_ar/descripcion-de-articulos/productos-recibe-notificaciones)

No se usaron blogs, foros, respuestas comunitarias ni llamadas a la API.

### Hechos demostrados

- `GET /users/{USER_ID}/items/search` lista publicaciones de la cuenta de un
  vendedor y admite filtros explícitos, incluido `status`.
- Para más de 1000 resultados se documenta `search_type=scan`, sin `offset`.
  El `scroll_id` expira en aproximadamente cinco minutos y debe reutilizarse
  hasta que el recorrido termine con valor `null`.
- La documentación de lifecycle reconoce `active`, `payment_required`,
  `under_review`, `paused`, `closed` e `inactive`. Seller search también
  documenta valores de filtro como `pending`, `not_yet_active` y `programmed`.
- `deleted` está documentado como substatus/acción posterior a `closed`, no como
  prueba de que una ausencia de seller search signifique eliminación.
- Los ítems finalizados pueden dejar de mostrarse después de un período, pero la
  documentación no vincula contractualmente ese comportamiento con una ausencia
  específica en `/users/{USER_ID}/items/search`.
- El topic general `items` notifica cambios y entrega un resource que debe
  consultarse mediante GET. Mercado Libre reintenta entregas no aceptadas durante
  una hora; tras ocho intentos las considera perdidas. `missed_feeds` conserva
  esas notificaciones por hasta dos días y exige `site_id` para el topic `items`.

### Hechos no demostrados

- Omitir `status` no tiene una afirmación contractual que enumere exhaustivamente
  todos los estados incluidos. Clasificación: `UNSPECIFIED`.
- `search_type=scan` no documenta snapshot isolation ni point-in-time
  consistency, ni el tratamiento de altas, cierres o eliminaciones concurrentes.
- `scroll_id` demuestra continuidad técnica de paginación, no autoridad sobre un
  universo inmutable.
- No se garantiza que ausencia signifique `closed`, `deleted`, `removed` o
  `inactive`; la visibilidad de removal en seller search es `UNSPECIFIED`.
- Las notificaciones no aportan por sí solas un estado terminal: informan el
  resource y requieren releerlo; además poseen una ventana finita de recuperación.

### Contrato fail-closed

`ML_COMPLETE_SCAN_EVIDENCE` significa exclusivamente evidencia técnica interna:

1. seller identity, Organization, Store y Connection fijas y validadas;
2. query sin filtros reductores;
3. paginación ejecutada mediante el modo oficial aplicable;
4. cada cursor seguido una vez y dentro de su vigencia;
5. final oficial alcanzado;
6. cero fallos terminales de provider, normalización o persistencia;
7. counters consistentes y vínculo durable `last_seen_sync_run_id`;
8. run original todavía vigente, no recuperado ni superado por otro run.

Esto permite marcar un Listing como `MISSING_CANDIDATE`: evidencia reversible de
que no fue observado bajo ese contrato. No equivale a
`AUTHORITATIVE_PROVIDER_SNAPSHOT` ni a `PROVIDER_CONFIRMED_REMOVAL` y nunca cambia
el status provider, borra la fila o afirma cierre/eliminación.

La evidencia positiva sí es segura: si el Listing reaparece en cualquier fetch
válido y persistido, conserva identidad, vuelve a `SEEN`, actualiza
`last_seen_sync_run_id` y limpia la evidencia de no observación.

`CONFIRMED_MISSING` continúa `DEFERRED`. Dos scans pueden aumentar evidencia
operacional, pero no convierten una semántica provider no documentada en certeza.

### Ajuste del diseño W-A

- Mantener `last_seen_sync_run_id`: sigue siendo la evidencia durable mínima para
  debugging, idempotencia, reappearance y protección contra old-run races.
- Reemplazar el nombre preliminar `authoritative_scan` por
  `reconciliation_eligible`. El campo expresa un gate interno para evidencia
  reversible y no promete snapshot authority del provider.
- Mantener los estados canónicos `SEEN` y `MISSING_CANDIDATE`. `PRESENT` afirmaría
  actualidad provider y `NOT_SEEN` describe un evento, no el estado acumulado.
- Renombrar la metadata preliminar de Listing a `not_seen_since` y
  `consecutive_not_seen_count`; son más exactos que `missing_since` y
  `missing_count`.
- Mantener `missing_candidate_count` y `reappeared_count` en el run: ambos tienen
  valor operacional y explican el efecto de una reconciliación sin crear eventos
  por cada Listing. No agregar `confirmed_missing_count`.

El schema propuesto para 2.20W-B queda limitado a:

- `listings.last_seen_sync_run_id uuid null`, con FK compuesta tenant/Store/
  Connection hacia `listing_sync_runs`;
- `listings.reconciliation_state` con `seen|missing_candidate`;
- `listings.not_seen_since timestamptz null`;
- `listings.consecutive_not_seen_count bigint not null default 0`;
- `listing_sync_runs.reconciliation_eligible boolean not null default false`;
- counters `missing_candidate_count` y `reappeared_count`;
- checks de coherencia, índice scoped y los mismos RLS/grants server-only de W-A.

Las filas legacy no reciben un run histórico inventado. Permanecen `seen` con
link nullable hasta una observación futura.

### Scope exacto autorizado para 2.20W-B

2.20W-B puede implementar captura run-aware de observaciones, cálculo de
eligibility técnica, transición reversible `SEEN ↔ MISSING_CANDIDATE`, counters
agregados y reconciliación/finalize atómicos dentro de Organization + Store +
Connection.

Quedan fuera: hard/soft delete, `CONFIRMED_MISSING`, declarar estados provider por
ausencia, cambiar `status`, mutaciones a Mercado Libre, webhooks/notificaciones,
scheduler y reconciliación global. Search y notificaciones son complementarios:
el futuro topic `items` aporta cambios positivos en tiempo real y `missed_feeds`
recuperación acotada; ninguno reemplaza al otro ni se implementa en W-B.
