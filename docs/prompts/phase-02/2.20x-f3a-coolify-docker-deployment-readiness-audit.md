# Fase 2.20X-F3-A — Coolify / Docker deployment readiness audit

Fecha: 2026-08-29. Estado: **READ-ONLY AUDIT PASS**.

## Decisión confirmada

El target canónico elegido para laboratorio y futuro production deployment es:

```text
Hostinger VPS
  -> Ubuntu LTS
  -> Docker
  -> Coolify
  -> e-ngenieria Hub
```

El laboratorio local Windows → WSL2 → Ubuntu 24.04 LTS → Docker Engine →
Coolify → Traefik → Next.js fue reportado como PASS. Esta evidencia demuestra
viabilidad local, no producción pública, TLS, dominio real, Hostinger VPS,
firewall, redirects OAuth, webhook real, migrations remotas ni scheduler.

## Objetivo y límites

Auditar read-only la preparación reproducible del repositorio para Docker y
Coolify, identificar gaps y definir la recomendación mínima para F3-B. No se
implementan Dockerfiles, healthchecks, triggers, scheduler, configuración
Coolify, variables reales, migrations remotas ni llamadas externas.

## Evidencia auditada

- Bun es el package manager canónico: existe sólo `bun.lock`, los scripts son
  compatibles y `.vscode/settings.json` declara `npm.packageManager = bun`.
- `bun run build` y `bun run start` son los comandos del repositorio. Para la
  imagen elegida, `BUILD_STANDALONE=true` produce el servidor autocontenido y
  el runtime recomendado es `node server.js`.
- Next.js usa App Router, SSR, Server Components y Route Handlers sobre runtime
  Node.js por defecto. No hay declaraciones Edge en las rutas auditadas.
- `Dockerfile` y `Dockerfile.bun` son heredados del starter. Ambos producen
  standalone, usan usuario no-root, exponen 3000 y fijan
  `HOSTNAME=0.0.0.0`; ninguno tiene `HEALTHCHECK`.
- No existen compose, configuración Coolify/Railpack, workflow de deployment
  ni health route. `public/` contiene sólo assets estáticos y no se detectaron
  uploads o escrituras productivas al filesystem local.
- Supabase se consume externamente mediante `supabase-js` y `service_role`
  server-only; no existe conexión PostgreSQL directa ni requisito de pool en el
  container.
- El callback público de items limita el body a 16 KiB, no usa Clerk, no llama
  al provider y responde con body vacío 200/503. Su autenticidad criptográfica
  continúa abierta por falta de un contrato oficial implementable.
- `runIncrementalEventMaintenance` es server-only, globalmente acotado a 45 s,
  deriva Connections desde DB y conserva locks, leases, CAS, checkpoints y
  reclaim stale de diez minutos. No existe trigger.

## Clasificación de containers

- `Dockerfile`: **ADJUST**. Es la base recomendada, pero debe fijar la versión
  de Bun, ejecutar el build con Bun, declarar todos los build args públicos,
  agregar healthcheck y endurecer el manejo de secretos/contexto.
- `Dockerfile.bun`: **DEPRECATE** y retirar más adelante una vez validada la
  imagen canónica. Mantener dos runtimes productivos aumenta divergencia sin
  aportar una necesidad actual.
- `.dockerignore`: **GAP**. Excluye `.env` y variantes locales, pero no cubre de
  forma general archivos como `.env.production`.

La estrategia recomendada para Coolify es **DOCKERFILE**, no Railpack: permite
fijar toolchain, mantener paridad local/VPS, inspeccionar el runtime standalone
y preparar futuros jobs sin depender de autodetección de buildpacks.

implementados; no se generó ningún valor en este audit.

## Gates externos, storage y seguridad

- Clerk requiere keys de producción, dominio/origins autorizados, URLs de
  sign-in/sign-up y Organizations configuradas para el dominio final. El proxy
  protege dashboard y APIs privadas; el callback de notifications permanece
  público por diseño.
- Supabase seguirá externo. URL y `service_role` se inyectan sólo en runtime;
  no hay cliente privilegiado browser-facing ni pooling PostgreSQL dentro del
  container. Las cinco migrations X-B/D/E/F/F2b siguen pendientes de remote.
- Mercado Libre requiere actualizar la redirect URI HTTPS exacta, el callback
  público de items y la configuración de la Developers Application al dominio
  final. El container necesita egress HTTPS para OAuth, `/users/me`, items y
  `missed_feeds`.
- No se requiere volumen persistente. Assets `public/` son image-owned y el
  cache `.next` puede ser efímero; un filesystem totalmente read-only requerirá
  un mount/tmpfs escribible para ese cache.
- Los runners actuales usan usuario no-root. F3-B todavía debe fijar imágenes y
  Bun, limitar capabilities/resources, definir restart policy y evitar secrets
  en layers o build args.
- Sentry desactiva PII por defecto y sanitiza headers, body, cookies, tokens y
  secrets. No se detectaron logs de tokens ni payloads raw. Faltan alertas del
  scheduled job, política de retención Coolify y revisar el sample rate de
  producción; además `removeConsole` elimina logs productivos no enviados a
  Sentry.

## Gaps antes de producción

1. Consolidar y endurecer el Dockerfile canónico, incluidos tags/versiones
   reproducibles, build args, `.dockerignore`, healthcheck y política Coolify
   de restart/resources.
2. Crear un health endpoint liviano que no dependa de Mercado Libre. `/` no es
   apropiado porque redirige según Clerk; la recomendación es `/api/health`.
3. Configurar el dominio HTTPS real en Coolify/Traefik y luego alinear Clerk,
   `NEXT_PUBLIC_APP_URL`, redirect OAuth exacta y callback público de Mercado
   Libre. El laboratorio local no valida estos gates.
4. Aplicar y validar por gate separado las migrations locales pendientes X-B,
   X-D, X-E, X-F y F2b antes de habilitar tráfico/event maintenance.
5. Implementar el trigger F3-B como Coolify scheduled job cada cinco minutos
   hacia un Route Handler interno machine-authenticated. El request no acepta
   IDs de tenant/Store/Connection. El path se bloquea en Traefik para tráfico
   público y usa Bearer secret runtime sólo como defensa M2M interna.
6. Agregar observabilidad del trigger y alertas de fallos/stale. Los maintenance
   runs son evidencia durable, pero no sustituyen logs operativos ni detección
   de un job que nunca inició. Revisar también el muestreo Sentry productivo.
7. Definir backups, firewall VPS, rotación de secretos y rollback operativo de
   Coolify. Rollback de imagen no equivale a rollback de schema; las migrations
   se corrigen forward-only.

## Estrategia de deployment y rollback

Flujo mínimo recomendado:

```text
GitHub -> Coolify build immutable image -> preflight/backup
       -> controlled Supabase migration job -> deploy candidate
       -> /api/health -> switch traffic -> enable scheduled job
```

No se ejecutan migrations al arrancar la app. Un rollback restaura la imagen
anterior y deshabilita el scheduled job; no revierte automáticamente DB ni
webhooks. Los cambios de schema deben ser compatibles con la versión anterior
o recibir una migration forward correctiva.

## Resultado

La arquitectura es apta para Hostinger VPS + Docker + Coolify, pero el repo no
está production-ready sin los gaps anteriores. El audit queda **PASS** y la
recomendación es `READY_FOR_2_20X_F3B_COOLIFY_DOCKER_IMPLEMENTATION`.
