# Fase 2.20U — Administrative stale-run recovery

## Objetivo

Incorporar una recuperación administrativa explícita, tenant-bound,
idempotente y auditable para `listing_sync_runs` stale, sin repetir trabajo del
provider. Este bloque continúa el contrato cerrado en
[2.20T](./2.20t-sync-run-orchestration-observability.md).

## Invariantes y alcance

- Sólo Owner y Manager persistentes pueden inspeccionar o recuperar runs.
- El servidor resuelve Organization y recovery actor; el request aporta sólo
  run ID, outcome terminal y reason controlados.
- Sólo un run `running` sin checkpoint durante al menos 15 minutos es stale.
- `succeeded` requiere evidencia persistida completa; `failed` permite liberar
  explícitamente un run stale con estado incierto.
- El actor original, counters y checkpoint se preservan. El recovery actor vive
  en auditoría.
- La transición y sus audits son atómicos; un segundo intento no muta ni duplica
  eventos.

## Decisiones

- Threshold server-side: `LISTING_SYNC_RUN_STALE_AFTER_MS = 15 * 60 * 1000`,
  muy por encima del timeout/retry unitario vigente y medido desde el último
  checkpoint, no desde la duración total.
- Clasificaciones: `RECOVERABLE_AS_SUCCEEDED`, `RECOVERABLE_AS_FAILED`,
  `NOT_RECOVERABLE` y `NOT_STALE`.
- Outcomes terminales administrativos: `succeeded` y `failed`; `partial` queda
  fuera porque los counters no permiten inferirlo inequívocamente.
- Reasons: `FINALIZE_INTERRUPTED`, `PROCESS_CRASHED`, `MANUAL_ABORT` y
  `UNKNOWN_EXECUTION_STATE`.
- Se reutilizan `listing_sync_runs` y `audit_events`; no se agregan columnas. Una
  migration forward-only agrega la RPC atómica y el error code
  `administrative_recovery`.
- Se emite el audit terminal canónico y `listing.sync.recovered`, ambos una sola
  vez y con el recovery actor.

## Exclusiones

No se implementan scheduler, worker, auto-recovery, resumability, provider
calls, OAuth, refresh, reconnect, UI completa ni cambios remotos.

## Checkpoint

Implementación local completa. Se agregó una route GET/POST server-only,
permission específica Owner/Manager, read model seguro, repository tenant-bound
y RPC atómica service-role-only. No se agregó UI, scheduler, worker, cursor ni
columnas de recovery.

Validación: tests focalizados 43/43 PASS; suite completa 213/213 PASS;
typecheck PASS; lint PASS; `supabase db reset` PASS; matriz de regresión 2.20T
22/22 PASS; matriz 2.20U 12/12 PASS con rollback. No se ejecutó build porque no
cambió UI ni runtime de bundling. No hubo remoto, Mercado Libre, OAuth,
reconnect, refresh, migration remota ni cierre Git.

## Validación remota autorizada

Se autoriza aplicar remotamente sólo la migration 2.20U y validarla con
fixtures sintéticos tenant-bound. Antes del write deben comprobarse history,
schema y ausencia de runs reales stale; ningún run, Listing, Connection o
credencial real puede usarse o modificarse. Provider calls, OAuth, reconnect y
refresh permanecen prohibidos. El resultado remoto y el cleanup se agregarán
al finalizar esta validación controlada.

## Resultado remoto controlado

El precheck confirmó history alineado hasta 2.20T, un dry-run con sólo la
migration 2.20U, tres runs históricos y cero runs `running` o stale. La
migration `20260827081922` se aplicó por el mecanismo canónico y el history
posterior quedó alineado. El schema remoto confirmó firma y return shape,
`SECURITY DEFINER`, `search_path=pg_catalog`, RLS y grants exclusivos de
`service_role`; los accesos públicos sin credenciales respondieron 401.

La validación usó 18 filas base sintéticas tenant-bound y produjo cuatro audits
de recovery. Owner y Manager pasaron; Employee, Client y cross-tenant fueron
rechazados. Store/Connection inconsistentes fallaron por constraint. Succeeded,
failed, `not_stale`, `not_recoverable`, `already_terminal`, preservación de
counters/checkpoint/actor, audits únicos, atomicidad y liberación del running
gate pasaron. Una prueba focalizada 1/1 del servicio administrativo contra la
DB remota clasificó un run stale incompleto como `RECOVERABLE_AS_FAILED` sin
exponer actor, idempotency key, error summary ni campos sensibles.

Un primer batch sintético fue rechazado antes de crear runs porque PostgREST
exigía claves uniformes; su cleanup dejó cero filas antes del retry. El cleanup
final también dejó cero fixtures. Los conteos reales volvieron al baseline:
membership, Store, Connection, Listing y secret en 1; audits en 10; runs en 3;
cero `running` y cero stale. No hubo provider calls, OAuth, reconnect, refresh,
recovery real, cambios de Listings/credenciales reales ni cierre Git.

Resultado: `REMOTE_2_20U_VALIDATION_PASS`. Recomendación:
`READY_TO_CLOSE_2_20U`.

## Cierre Git autorizado

La migration remota fue aplicada y la matriz de seguridad pasó. Recovery a
`succeeded` y `failed` pasó; el segundo intento devolvió `ALREADY_TERMINAL`.
El cleanup sintético pasó y hubo cero provider calls. Con
`REMOTE_2_20U_VALIDATION_PASS`, queda autorizado el cierre Git de 2.20U.
