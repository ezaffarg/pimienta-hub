# Fase 2 — 2.20Q Bind reconnect pending target

## Implementación aprobada

La capa de base de datos agrega `target_connection_id` nullable a
`oauth_pending_authorizations`, con FK restrictiva hacia `connections(id)`.
El CHECK de reconnect se crea `NOT VALID`: las filas legacy no se modifican ni
se reutilizan, y las nuevas escrituras con `purpose = reconnect` requieren un
target. `connect` puede conservar target NULL. No hubo backfill ni acceso a la
pending real.

## Cierre local — finalización target-bound

La migration append-only
`20260825160000_bind_reconnect_finalization_target.sql` reemplaza la RPC para que
`reconnect` use exclusivamente `target_connection_id`, bloquee y valide esa
Connection y su Store, y nunca caiga en lookup o creación por provider e
identidad. El secreto existente se reemplaza atómicamente, incrementa
`credential_version` mediante el trigger vigente, limpia el lease, reactiva la
Connection, registra `integration.reconnected` y consume la pending al final.

`supabase db reset` y la matriz SQL local 13/13 pasaron con fixtures dentro de
`BEGIN / ROLLBACK`; no quedaron duplicados ni fixtures. No hubo remoto, OAuth,
refresh, finalización real ni acceso a la pending legacy.

## Validación remota controlada

aplicadas en el proyecto dedicado y la history remota está alineada. La matriz
sintética remota reducida pasó 8/8 dentro de `BEGIN / ROLLBACK`, con cero

pending legacy reales conservaron su estado. No hubo OAuth, refresh,
finalización real ni llamadas a Mercado Libre.
