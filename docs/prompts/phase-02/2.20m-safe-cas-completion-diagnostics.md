# Fase 2 — 2.20M: diagnóstico seguro de finalización CAS

## Mandato archivado

Contexto de partida: el único refresh real de 2.20K obtuvo un claim, una respuesta
válida del proveedor y credenciales rotadas en memoria, pero falló en
`CAS_COMPLETE / REFRESH_CAS_FAILED`. La versión remota permaneció en `1` y el
lease terminó libre. La investigación 2.20L reprodujo el flujo localmente con
éxito y verificó que migration, RPC y trigger coinciden entre local y remoto;
no confirmó causa histórica ni aplicó una migration. El refresh persistido real
se considera potencialmente consumido y no reutilizable.

Objetivo autorizado: distinguir exclusivamente en servidor un error de llamada
RPC de un rechazo CAS limpio, sin cambiar la semántica CAS. La clasificación
requerida es equivalente a `REFRESH_COMPLETE_RPC_FAILED`,
`REFRESH_CAS_REJECTED` y `CAS_COMPLETED`. Ante un rechazo se puede releer sólo
metadata segura: versión esperada/actual y presencia/coincidencia del lease;
nunca tokens, ciphertext, UUID del lease, secretos, headers o bodies.

Queda prohibido retirar versión o lease del `WHERE`, aceptar cualquier lease,
sobrescribir incondicionalmente, ignorar `false`, reintentar complete/refresh,
hacer una migration salvo STOP, usar el refresh real, reconnect, OAuth, listing
sync, escrituras remotas o cierre Git. Phase-01 y el prompt 2.20E se preservan.

La validación solicitada cubre: complete exitoso; error Supabase/RPC; `false`;
mismatch de versión; mismatch y ausencia de lease; redacción de secretos; y que
un fallo secundario de release no reemplace el error primario. Si surgiera una
causa histórica reproducible debe demostrarse primero por test; si requiriera
migration, detenerse.

## Resultado

El repositorio ahora separa explícitamente la excepción de `rpc(...)` del
resultado booleano de la función `complete_integration_secret_refresh`.
`false` dispara una relectura server-only de `credential_version` y del estado
del lease, sin devolver el UUID. La causa histórica de 2.20K sigue sin evidencia
preservada para clasificarla retrospectivamente.

No se alteró SQL, la protección stale-writer ni el comportamiento de refresh.
No se usaron credenciales reales, el remoto ni una base local para este cambio.

## Cierre — Safe CAS completion diagnostics

El cierre aprobado separa este alcance del registro histórico de Phase 01. El
error de llamada RPC queda clasificado como `REFRESH_COMPLETE_RPC_FAILED`; un
`false` confirmado por la RPC queda clasificado como `REFRESH_CAS_REJECTED` y
puede incluir sólo `expectedVersion`, `actualVersion`, `leasePresent` y
`leaseMatches`. No se expone el UUID del lease ni material secreto.

La causa del resultado real 2.20K permanece `STILL_UNKNOWN`; no se inventa una
explicación retrospectiva. CAS conserva versión, lease y expiración en su
condición, sin retry automático, migration, refresh real, reconnect ni listing
sync. El diagnóstico queda `READY_FOR_RECONNECT` únicamente para una futura
subfase autorizada de forma independiente.
