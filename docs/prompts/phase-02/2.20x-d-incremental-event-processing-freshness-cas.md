# Fase 2.20X-D — Incremental event processing & freshness CAS

Fecha: 2026-08-28. Estado: **LOCAL IMPLEMENTATION + VALIDATION PASS**.

## Objetivo y contratos heredados

Agregar capacidad server-only controlada para procesar eventos Mercado Libre
`items` ya persistidos por X-B/X-C. El callback conserva exactamente su trabajo:
validar, resolver, intake/dedupe y ACK, sin provider calls.

El processor debe claimar atómicamente un evento, reutilizar credenciales y el
cliente/normalizador vigentes, aplicar un Listing sólo mediante freshness CAS
basado en `provider_updated_at` y finalizar el lifecycle sin material sensible.

## Claim, freshness y retry

- lifecycle mínimo: `received → processing → processed|failed`;
- un lease/CAS impide procesamiento simultáneo y permite reclaim expirado;
- `newer → APPLY`, `older → STALE_NOOP`, igual equivalente →
  `EQUIVALENT_NOOP`, igual conflictivo o timestamp inválido → fail closed;
- fallos transitorios quedan retryable sin marcar processed;
- 404 no infiere status, ausencia, candidate ni eliminación;
- reaparición positiva limpia sólo evidencia negativa y preserva
  `last_seen_sync_run_id`.

## Exclusiones

No scheduler, polling, `missed_feeds`, public process route, worker automático,
provider calls reales, Listing sync real, remote apply/writes, OAuth/reconnect,
UI ni cierre Git. Los provider responses son mocks/fixtures.

`service_role`. El processor controlado recibe sólo `eventId`, revalida el
binding persistido, reutiliza el credential service y el client/normalizador
