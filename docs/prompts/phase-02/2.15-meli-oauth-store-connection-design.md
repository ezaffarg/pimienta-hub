### Roles y autorización de Connections

El modelo canónico mantiene exactamente `Owner`, `Manager`, `Employee` y `Client`; no se agregan `Administrator` ni `Operator`.

- Owner: puede conectar y reconectar cualquier Store de su Organization.
- Manager: puede conectar y reconectar cualquier Store de su Organization.
- Employee: inicialmente no administra Connections/OAuth.
- Client: puede hacer self-onboarding y reconnect de su propia cuenta/Store, sin administración global.

Clerk gestiona registro, login, contraseña, MFA y sesión. e-Hub no almacena contraseñas propias. La coincidencia de email entre la cuenta Mercado Libre y el Client puede ayudar al onboarding, pero nunca demuestra propiedad: la prueba técnica sigue siendo OAuth oficial → `GET /users/me` → user ID.

El onboarding objetivo de Client es: invitación/alta → Clerk → membership persistente Client → ausencia de assignment → onboarding requerido → OAuth → identidad real → confirmación de Store → Store + Connection + `store_assignment` → dashboard. El onboarding administrativo Owner/Manager puede realizar la conexión y asignar usuarios después. Cada Employee conserva identidad Clerk, membership y assignments propios; no se comparte el login de Mercado Libre.

### Store, Connection e idempotencia

Se mantiene `Organization → Store → Connection → Provider`, con `external_account_id = id` de `GET /users/me` y nickname sólo como display. La misma combinación provider + external account no debe generar duplicados históricos silenciosos. Connection activa existente no crea otra Store/Connection; Connection disabled se reactiva preferentemente. El índice parcial actual sólo para `active` no es la política definitiva y requiere revisión de schema antes de OAuth real. Cross-tenant se deniega y una reasignación a otra Store requiere flujo administrativo explícito; nunca es automática.

Onboarding administrativo: Store + Connection atómicos. Self-onboarding Client: Store + Connection + assignment atómicos/coherentes. No se implementa todavía.

### OAuth y secretos

Authorization Code server-side, `GET /users/me` como identidad, state opaco criptográfico server-side, expirable, single-use y vinculado al actor, Organization y propósito. PKCE se usa sólo si la aplicación/documentación oficial lo soporta o requiere. Access y refresh tokens son server-only; no aparecen en Client Components, localStorage, cookies legibles, Git, logs ni audit logs. Secure secret storage queda pendiente de 2.16+ y no se crea migration en 2.15.

### Audit foundation

e-ngenieria Hub tendrá Audit Log interno con control server-side:

- Owner: `audit:read` permitido.
- Manager: `audit:read` permitido.
- Employee y Client: denegado.

Las mutaciones futuras deberán poder atribuir WHO, WHAT, WHEN, Organization, Store y recurso. Se consideran eventos: preguntas, publicaciones, precio, stock, promociones, OAuth connect/disconnect/reconnect, configuración, usuarios, roles, assignments, exportaciones y acciones administrativas. El metadata será allowlisted y sanitizado; nunca guardará passwords, tokens, códigos, cookies, service keys, secretos ni bodies completos con PII innecesaria. Una futura tabla `audit_events` y su foundation son requisitos previos a mutaciones ML productivas; no se crea ahora.
