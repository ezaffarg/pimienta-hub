# Fase 2 — 2.20O: soporte de reconnect para Connection activa

## Mandato archivado

Una Connection Mercado Libre activa puede requerir reautorización cuando sus
credenciales ya no son reutilizables. El runtime actual la rechaza como
`already_connected` antes de crear una pending authorization; 2.20O autoriza el
cambio mínimo para que un caller que solicite explícitamente `purpose=reconnect`
pueda reutilizar una Connection existente del mismo tenant y provider, activa o
deshabilitada.

El connect normal debe conservar `active -> already_connected`. Reconnect no se
infiere automáticamente, exige un target existente y falla cerrado si falta, es
cross-tenant, tiene provider diferente o la identidad obtenida no coincide con
la cuenta ya vinculada. La preparación no debe crear Store ni Connection; la
finalización reutiliza la Connection, conserva la semántica de
`credential_version` y audita `integration.reconnected`.

Quedan prohibidos OAuth, pending authorization, refresh, reconnect, token
exchange, `/users/me`, writes remotos, migration, DB push, listing sync y cierre
Git reales. Se preservan sin cambios los prompts 2.20E, 2.20L y 2.20N.

## Resultado

La causa de 2.20N queda confirmada y corregida en el runtime: el rechazo
`already_connected` ya aplica a connect normal, no a reconnect explícito. Para
reconnect, el callback exige target existente de la misma Organization,
provider `mercado-libre` e `external_account_id` idéntico al resultado
normalizado de `/users/me`. Un target ausente devuelve
`RECONNECT_TARGET_NOT_FOUND`; mismatch de tenant, provider o identidad falla
cerrado como conflicto. No hubo OAuth, pending, refresh, reconnect, llamadas
reales, migraciones ni writes remotos.

## Cierre — Active Connection Reconnect Support

El soporte quedó validado con tests focalizados: connect normal conserva
`already_connected`; reconnect explícito sobre target activo o disabled del mismo
tenant pasa a pending segura; un target ausente devuelve
`RECONNECT_TARGET_NOT_FOUND`; tenant, provider e identidad no coincidentes
fallan cerrados. La preparación no crea Store ni Connection y la finalización
existente reutiliza la Connection con la semántica vigente de versión y audit.

No hubo migration, OAuth, refresh, reconnect, listing sync, escritura remota ni
se modificaron los prompts 2.20E, 2.20L o 2.20N.
