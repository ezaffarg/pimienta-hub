## Connect route y política

Crear una route coherente, por ejemplo `POST /api/integrations/mercado-libre/connect`. Exige sesión Clerk y deriva server-side user, Organization activa, membership persistente, rol y permisos. ## Callback y persistencia pendiente

Crear callback GET coherente. Procesa sólo `code`, `state` y `error`; no authority params. Ante denial, normaliza sin token exchange ni pending y gestiona state contra replay.

Orden obligatorio: callback → validar state/expiry/no consumo/provider/actor-org binding → consumir de forma segura → token exchange. El callback requiere sesión Clerk correspondiente al actor y Organization del attempt; sin sesión, falla seguro y exige reiniciar. State no es credencial suficiente.

El token exchange server-side usa `POST /oauth/token`, sin retry automático ni logs de code, secret, access/refresh tokens. La respuesta se valida con Zod y conserva únicamente access token, refresh nullable, `expires_in`, token type, scope opcional y user id opcional; no se persiste respuesta cruda. `GET /users/me` usa el access token server-side, valida `id` requerido y nickname opcional; normaliza `externalAccountId = String(id)` y `displayName = nickname`, nunca email.

Después se cifran tokens, se calcula expiry y se crea una pending authorization bound a Organization, actor, provider, purpose, identidad externa y display, con TTL 20 minutos y sin plaintext. El browser recibe sólo `READY_FOR_ONBOARDING`, identificador opaco si fuera necesario y display UX; nunca tokens ni identidad técnica innecesaria. Toda finalización futura vuelve a verificar sesión, Organization, membership y binding; UUID no es bearer auth.
