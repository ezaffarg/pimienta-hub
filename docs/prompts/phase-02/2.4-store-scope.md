### Política canónica

- Owner: todas las Stores de su Organization, implícito, sin assignments.
- Manager: todas las Stores de su Organization, implícito, sin assignments; no equivale a Owner y conserva permissions distintas.
- Employee: solo Stores de `store_assignments`; cero assignments implica scope vacío.
- Client: solo Stores de `store_assignments`; cero assignments implica scope vacío.
- Default deny; jamás interpretar array vacío como todas las Stores y no inventar assignments.

Permission y Store Scope son conceptos separados: operar requiere permission adecuada **y** Store dentro del scope. Client scope no concede permisos globales.

Crear un resolver server-only único (`resolveStoreScope` o equivalente) que reciba contexto autenticado tenant + membership/Hub Role y exprese explícitamente `allStores: true` o IDs autorizados. Crear helper de acceso seguro. Cross-tenant debe deny/not found según contrato existente; misma Organization fuera de assignments es deny. No revelar recursos cross-tenant.

Los listados Owner/Manager usan `StoreRepository.listByOrganization(organizationId)`; Employee/Client reciben solo Stores de assignments, filtradas server-side. Si hace falta, agregar primitive por IDs siempre con `organizationId`; nunca get global por Store ID. Integrar con el tenant context existente: Organization desde Clerk server-side; browser no controla Organization, membership, role ni scope. Mantener fallback Clerk transitorio, pero un `org:member → Employee` no inventa assignments ni amplía acceso: seguridad prevalece sobre demos.

La jerarquía es Organization Scope → Store Scope → Resource; Store Scope complementa, no reemplaza Organization Scope. Mantener 401 sin auth, 403 sin permiso/scope y 404 seguro para inexistencia/cross-tenant según contrato existente.
