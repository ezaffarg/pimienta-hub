# Internacionalización

## Contrato vigente

Pimienta Hub usa `next-intl` con App Router y sin prefijo de locale en la URL
(`COOKIE_NO_PREFIX`). Los locales canónicos son `es-419`, `pt-BR` y `en`; el
default es `es-419`, el fallback estructural es `en` y la cookie reservada es
`pimienta_locale`.

La resolución server-side es determinista:

1. locale explícito válido;
2. cookie válida;
3. `Accept-Language`, por calidad, con `es* → es-419`, `pt* → pt-BR` y
   `en* → en`;
4. `es-419`.

Los valores explícitos y de cookie requieren coincidencia exacta con la
allowlist. Entradas ausentes, malformadas o no soportadas nunca llegan a rutas
de importación y resuelven al siguiente nivel o al default.

## Catálogos y runtime

`src/i18n/messages/<locale>/index.ts` compone los namespaces `common`,
`navigation` y `shell`. `load-messages.ts` usa imports estáticos allowlisted y
una combinación profunda, determinista y no mutante: parte del catálogo inglés
y aplica los overrides del locale seleccionado. En desarrollo, una clave que
falta también en inglés muestra su ruta para facilitar diagnóstico; en
producción devuelve un texto seguro sin detalles internos.

`src/i18n/request.ts` es el boundary de request de `next-intl`. El root layout
obtiene allí el locale, lo refleja en `<html lang>` y genera metadata traducida
con la API server. No existe provider global: Server Components son el camino
por defecto. El dashboard entrega únicamente `navigation` y `shell` mediante
un provider acotado a sus Client Components; `common` y futuros catálogos de
features no se serializan en ese boundary.

Las claves usan nombres semánticos por dominio, por ejemplo
`common.actions.save` y `navigation.products`; no contienen el texto fuente.
Locale de interfaz, moneda y zona horaria son contratos independientes.
La configuración conserva `UTC` como zona explícita común; no la infiere del
locale.

## Integración del shell global

La configuración de navegación conserva `title`, `url`, shortcuts y reglas
`access` como contratos internos estables. `labelKey` identifica sólo la copia
visible y `src/i18n/shell.ts` crea `displayTitle`/`displayLabel` al renderizar;
los textos traducidos nunca funcionan como IDs, rutas ni claves de permisos.

Los breadcrumbs traducen segmentos estáticos conocidos y preservan valores
dinámicos, nombres y contenido externo. El mismo catálogo acotado alimenta
sidebar, header, organización, theme controls, command palette, búsqueda,
chrome del panel informativo y chrome de notificaciones. El cuerpo de las
notificaciones continúa siendo contenido de feature. No hay cambio de URL ni
resolución de locale en el browser.

Los layouts raíz y dashboard resuelven su metadata con APIs server-side. Los
loading states activos del shell son skeletons sin copy visible; el error root
especial y los errores/validaciones de features no se migran en este slice.

## Selector y persistencia

El selector visible vive en el área de preferencias del usuario, dentro del
footer del sidebar. Ofrece exactamente `Español (Latinoamérica)` (`es-419`),
`Português (Brasil)` (`pt-BR`) y `English` (`en`), y refleja el locale canónico
resuelto por el servidor; no consulta `navigator.language`.

La Server Action `setLocalePreference` trata el valor como input no confiable y
sólo escribe un locale de la allowlist. La cookie `pimienta_locale` usa
`path=/`, `SameSite=Lax`, `HttpOnly=false`, `Secure` sólo en producción y
`maxAge=31.536.000` segundos (365 días). No accede a DB, Clerk metadata,
Organization, Store ni permisos.

Tras una escritura exitosa el cliente ejecuta `router.refresh()`: los Server
Components vuelven a resolver el locale y la ruta, pathname y search params no
cambian. La cookie conserva la preferencia durante navegación cliente, refresh
y recarga completa. Si la escritura falla, no se refresca ni se simula éxito;
si una cookie almacenada es inválida, se ignora y continúa la resolución
canónica por `Accept-Language` y default.

## Clerk

El mismo locale canónico selecciona un recurso oficial de
`@clerk/localizations@4.6.4`: `es-419 → es-MX` (`esMX`) como variante oficial
latinoamericana más cercana, `pt-BR → pt-BR` (`ptBR`) y `en → en-US` (`enUS`).
Los imports server-side por subpath cargan sólo el recurso elegido y
`ClerkProvider` lo recibe tipado; los catálogos de Pimienta Hub no se duplican
ni se mezclan con los de Clerk.

Este alcance localiza componentes Clerk embebidos en la aplicación. No intenta
localizar Account Portal alojado, páginas externas del provider ni Mercado
Libre OAuth. Clerk tampoco usa una detección de locale independiente.

## Slices posteriores

Quedan fuera la persistencia cross-device, formularios, Zod, toasts de features
y cualquier migración de formatos de fecha, número o moneda.
También permanecen sin traducir nombres de organización, Store, listing,
usuario y provider. Cada slice futuro debe ampliar primero el catálogo inglés,
mantener paridad de claves y enviar al browser sólo los mensajes estrictamente
necesarios.
